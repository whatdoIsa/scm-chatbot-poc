# SCM 자연어 질의 챗봇 PoC

한국어 SCM 질문을 로컬 LLM이 SQL·되묻기·거부 중 하나로 바꾸고, 서버가 검증한 뒤 읽기 전용 계정으로 실행해 결과를 돌려준다.
이 저장소의 핵심 산출물은 챗봇 화면이 아니라 **30문항 골든셋으로 잰 정확도와, 프롬프트 v0 → v1 → v2의 비교**다.
`poc-freeze` 태그 이후에는 **v3(라우터 분리, 조회 도구, 답변 문장과 숫자 후검증)** 을 같은 방식으로 재서 더했다.

- 모델: 로컬 Ollama `qwen2.5-coder:7b`, temperature 0, seed 42
- 스택: Java 21, Spring Boot 3.5, PostgreSQL 16, MyBatis, JSqlParser, React + TypeScript + Vite
- 문서: [docs/PRD.md](docs/PRD.md), [docs/API_SPEC.md](docs/API_SPEC.md), [AGENTS.md](AGENTS.md)

## 결과 요약

| 세트 | v0 | v1 | v2 | v3 |
| --- | --- | --- | --- | --- |
| 기본 30문항 (동결 후 측정) | 7 / 30 = 0.2333 | 22 / 30 = 0.7333 | 19 / 30 = 0.6333 | 23 / 30 = 0.7667 |
| 심화 20문항 (결과를 본 뒤 작성) | 5 / 20 = 0.2500 | 11 / 20 = 0.5500 | 9 / 20 = 0.4500 | 11 / 20 = 0.5500 |
| 홀드아웃 20문항 (v3 구현 전에 동결) | 3 / 20 = 0.1500 | 13 / 20 = 0.6500 | 11 / 20 = 0.5500 | 16 / 20 = 0.8000 |

- v0는 테이블 구조와 출력 형식만 준 기준선이다. v1은 기준일, 기간 규칙, 지표 사전, 예시 5개를 더했다. v2는 v1에 스키마 축소, SQL 검증, 실행 오류 재시도를 더했다. v3은 라우터가 질문을 조회 도구·SQL·되묻기·거부로 먼저 나누고, 조회 결과를 문장으로 옮긴 뒤 숫자를 대조한다.
- v0 → v1의 상승은 기간 집계에서 가장 크다(0 / 8 → 7 / 8). 지표 계산은 v1에서도 2 / 6에 머문다. v2는 세 세트 모두 v1보다 낮다.
- v3은 기본·심화 세트에서 v1과 같은 수준이고(1문항, 0문항 차이) 홀드아웃 세트에서 3문항 높다. 문항 수가 적고 1회 측정이라 2 ~ 3문항 차이는 우열로 단정하지 않는다.
- v3이 바꾼 것은 총점보다 오답의 종류다. v1에서 틀리고 v3에서 맞은 10문항 중 9문항이 조회 도구로 답한 지표·순위 질문이고, v1에서 맞고 v3에서 틀린 6문항은 모두 도구를 잘못 고른 경우다.
- 숫자 후검증 통과율은 세 실행 모두 100%였지만, 조회 자체가 틀린 문항의 문장도 전부 통과했다. 통과율은 "문장이 맞다"가 아니라 "숫자를 지어내지 않았다"만 뜻한다.

## 실행 방법

필요한 것: Java 21, Docker(Compose), Ollama와 `qwen2.5-coder:7b`, Node 22.

```bash
cp .env.example .env            # change-me 값을 바꾼다
set -a; . ./.env; set +a
bash scripts/db_reset.sh        # Postgres 컨테이너 + 스키마 + 시드
bash scripts/verify_db.sh       # 시드 검증 23개 항목
bash scripts/eval_restore.sh    # (선택) 저장된 측정 결과를 DB에 넣는다
```

백엔드와 화면은 터미널을 따로 열어 저장소 루트에서 각각 실행한다.

```bash
# 터미널 1: 백엔드 http://localhost:8080
set -a; . ./.env; set +a
(cd backend && ./gradlew bootRun --args='--chat.llm.provider=ollama')
```

```bash
# 터미널 2: 화면 http://localhost:5173
(cd frontend && npm ci && npm run dev)
```

`--chat.llm.provider`를 주지 않으면 모델 없이 동작하는 `fake`가 쓰인다. 프롬프트 버전은 `--chat.prompt-version=v0|v1|v2|v3`(기본 v1). 답변 문장과 도구 경로를 화면에서 보려면 `--chat.llm.provider=ollama --chat.prompt-version=v3`으로 띄운다.

테스트와 평가

아래는 모두 저장소 루트에서 실행한다(`.env`를 읽어 둔 상태).

```bash
(cd backend && ./gradlew test)                  # 단위 테스트 (DB, 모델 불필요)
(cd backend && ./gradlew integrationTest)       # 통합 테스트 (DB, Ollama 필요)
(cd backend && ./gradlew bootRun --args='--spring.profiles.active=eval --chat.llm.provider=ollama --eval.versions=v0,v1,v2')
bash scripts/final_check.sh                     # 동결 전 전체 점검
```

평가 실행은 `eval/golden_set.sha256`과 골든셋의 해시가 다르면 시작하지 않는다. 심화 세트는 `--eval.golden-path=../eval/golden_set_deep.json --eval.golden-hash-path=../eval/golden_set_deep.sha256`를 붙이고, 홀드아웃 세트는 같은 방식으로 `golden_set_v3.json`, `golden_set_v3.sha256`을 준다. v3 평가는 `--eval.versions=v3`.

## 설계 요약

```
질문 ─▶ PromptBuilder(v0|v1|v2) ─▶ Ollama(JSON 스키마 강제) ─▶ LlmOutputParser
                                                                 │ action
                         clarify / refuse ◀──────────────────────┤
                                                                 ▼ sql
        (v2) SqlValidator ─▶ ReadOnlySqlExecutor(scm_ro) ─▶ 결과 + chat_log
                 │ 실행 오류 (v2, 1회)
                 └──▶ PostgreSQL 오류를 붙여 다시 질문
```

v3은 같은 서버에 경로를 하나 더한 것이다(v0 ~ v2의 프롬프트와 동작은 그대로다).

```
질문 ─▶ 라우터(LLM 1회) ─┬─ clarify / refuse ─▶ message
                         ├─ tool ─▶ 인자 검증 ─▶ MyBatis 고정 쿼리(scm_ro) ─┐
                         └─ sql  ─▶ v1 프롬프트로 SQL 생성 ─▶ SqlValidator   │
                                    ─▶ 읽기 전용 실행(오류 시 1회 재시도) ───┤
                                                                             ▼
                        결과 1~20행 ─▶ 답변 문장(LLM 1회) ─▶ 숫자 후검증 ─▶ 응답
```

- **라우터**: 질문과 무관하게 고정된 프롬프트로 경로만 고른다. DDL 대신 데이터 요약, 기간 규칙, 도구 목록을 준다.
- **조회 도구 6개**: 지표 정의 6개(일평균 판매량, 재고보유일수, 결품률, 예측 정확도, 안전재고 미달, 재주문 필요)를 MyBatis 고정 쿼리로 옮겼다. 모델이 정하는 것은 도구 이름과 인자(품목, 거점, 일수, 기간, 출력 방식, 순위 개수)뿐이고, 인자는 검증을 거쳐 바인딩 파라미터로만 들어간다. LLM이 만든 SQL은 JDBC로, 정의가 고정된 지표는 MyBatis로 실행한다.
- **도구는 자기 지표 값만 돌려준다.** 재고나 일평균 같은 구성 요소를 함께 내면, 도구를 잘못 골라도 채점의 추가 컬럼 허용 규칙 때문에 정답 처리될 수 있어 뺐다.
- **인자 검증에 실패하면 `TOOL_REJECTED`로 끝낸다.** SQL 경로로 넘기지 않는다. 라우터의 인자 오류를 그대로 재기 위해서다.
- **숫자 후검증**: 답변 문장의 숫자가 결과 셀(반올림·버림 허용), 질문, 도구 인자, 날짜, 행 수 중 하나에서 왔는지 본다. 아니면 문장을 버리고 표만 응답한다.

- **세 가지 action**: 모델은 `sql`, `clarify`, `refuse` 중 하나를 JSON으로 낸다. 형식은 Ollama의 structured output으로 모든 버전에서 똑같이 강제한다.
- **쓰기 차단은 여러 겹이다.**
  1. DB 계정 `scm_ro`는 `scm` 스키마 6개 테이블의 SELECT 권한만 가진다. 로그·평가 테이블이 있는 `app` 스키마에는 권한이 없다.
  2. 실행기는 읽기 전용 트랜잭션에서 실행하고 항상 롤백한다. SQL이 세션 설정을 바꿔도 풀의 커넥션에 남지 않는다.
  3. 드라이버 쿼리 타임아웃 5초. SQL이 `statement_timeout`을 풀어도 취소된다.
  4. (v2) `SqlValidator`가 단일 SELECT, 허용 테이블, 허용 함수 목록, LIMIT 200을 확인한다.
- **기준일 고정**: 데이터의 마지막 날 2026-11-08을 "오늘"로 본다. v1부터 프롬프트에 기준일과 기간 규칙을 넣는다.
- **채점**: 생성 SQL의 실행 결과를 정답 SQL의 실행 결과와 값으로 비교한다. 컬럼명과 컬럼 순서는 보지 않고, 생성 결과에 라벨 컬럼이 더 있어도 된다. 숫자는 상대 오차 0.1%까지 같은 값이다.
- **채점기 자체 검증**: 정답을 그대로 돌려주는 `oracle` provider로 평가하면 30 / 30이 나와야 한다. v0·v1·v2 경로(v2는 검증기와 LIMIT 적용) 모두 30 / 30, 심화 세트 20 / 20이며 CI가 매번 확인한다.
- **골든셋 동결**: 측정 전에 SHA-256을 기록하고, 평가 실행기는 해시가 다르면 실행을 거부한다.
- **결정적 시드**: 난수 대신 `hashtextextended`로 값을 만들어 다시 생성해도 테이블 체크섬이 같다.

| 기본 (실행 140) | 25 | 0 | 0 | 7 |
| 심화 (실행 141) | 12 | 0 | 0 | 5 |
| 홀드아웃 (실행 145) | 17 | 0 | 0 | 4 |

- 통과율은 세 실행 모두 1.0000이다. 이 모델은 결과 표에 없는 숫자를 지어내거나 새로 계산한 문장을 한 번도 쓰지 않았다. 후검증이 걸러 낸 것이 없다는 뜻이기도 하다.
- 통과한 문장 54개 가운데 16개는 조회 자체가 틀린 문항의 문장이다. 후검증은 숫자의 출처만 보므로 이런 문장을 막지 못한다. 문장이 붙으면 틀린 조회가 더 그럴듯하게 보인다는 점이 오히려 위험하다.

## 오답 사례와 변경

### 1. 기준일이 없어 날짜를 추측한다 (DATE_RANGE)

- 질문: Q07 "어제 서울센터 전체 판매량은?"
- v0 생성 SQL: `... WHERE sale_date = CURRENT_DATE - INTERVAL '1 day' ...`
- 원인: 프롬프트에 "오늘"이 없어 실제 시계를 썼다. 데이터의 마지막 날은 2026-11-08이라 값이 다르다.
- 변경(v1): 기준일과 기간 규칙(어제, 최근 N일, 이번 주, 지난주, 이번 달, 지난달)을 넣고 `CURRENT_DATE`를 쓰지 말라고 지시했다.
- 결과: DATE_RANGE 오답이 9건에서 1건으로 줄었다. 기간 집계 유형은 0 / 8에서 7 / 8이 됐다. 남은 1건(Q13)은 "최근 30일"의 시작일을 하루 이틀 틀린 것이다.

### 2. 거점 이름과 SKU 표기를 값 그대로 넣는다 (SCHEMA_MISUNDERSTANDING)

- 질문: Q04 "SKU-7의 카테고리와 ABC 등급은?", Q12 "이번 달 부산센터 SKU-009 판매량은?"
- v0 생성 SQL: `WHERE sku = 'SKU-7'`, `WHERE location_id = '부산센터'`
- 원인: SKU 표기 규칙과, 거점은 이름으로 찾아 ID로 조인한다는 점을 스키마만으로는 알 수 없다.
- 변경(v1): 단위 규칙("SKU-7은 SKU-007로 정규화")과 용어 사전("거점 이름은 location.name으로 찾는다")을 넣었다.
- 결과: SCHEMA_MISUNDERSTANDING 3건이 0건이 됐다.

### 3. 지표를 자기 방식으로 계산한다 (METRIC_DEFINITION)

- 질문: Q20 "최근 28일 SKU-029의 일평균 판매량은?"
- 생성 SQL(v0, v1, v2 모두): `SELECT AVG(qty) ...`
- 원인: 정의는 "기간 내 판매 합 ÷ 일수"인데 `AVG(qty)`는 거점-일 행의 평균이라 5분의 1 수준이 나온다.
- 변경(v1): 지표 사전에 정의를 넣고 "AVG(qty)를 쓰지 않는다"고 적었다.
- 결과: **고쳐지지 않았다.** 세 버전 모두 `AVG(qty)`를 썼다. 지표 정의 오답은 6건에서 3건으로 줄었지만 결품률(Q16), 일평균(Q20), 예측 정확도 순위(Q21)는 남았다. 정의를 문장으로 주는 것만으로는 부족하고, 지표별 SQL 템플릿이나 조회 도구가 필요해 보인다.

### 4. SQL 실행 오류는 재시도로 일부만 줄어든다 (SQL_EXECUTION_ERROR)

- 질문: Q19 "SKU-008의 최근 13주 예측 정확도는?"
- v1 생성 SQL: `sales_daily`에서 없는 컬럼 `week_start`를 참조해 실행 오류.
- 변경(v2): PostgreSQL 오류 문구를 붙여 한 번 더 묻는다.
- 결과: v2도 같은 오류를 냈고 재시도(모델 호출 2회)에서도 정답을 만들지 못했다. 이 모델은 "일별 판매를 주 단위로 묶어 예측과 맞춘다"는 단계를 오류 문구만으로는 만들지 못했다.

### 5. v2가 v1보다 낮아진 문항

- Q05, Q24, Q25, Q30은 v1에서 맞고 v2에서 틀렸다. Q15는 반대로 v2에서만 맞았다.
- v2는 질문마다 프롬프트의 스키마·지표 부분이 달라진다. Q24는 재고보유일수 순위에 `abc_class = 'A'` 조건을 임의로 넣었고, Q25("재고 어때?")와 Q30(영업이익)은 되묻거나 거부하지 않고 SQL을 냈다.
- 원인은 확정하지 못했다. 문맥이 줄면서 "되묻기·거부" 판단의 근거가 약해졌을 가능성이 있지만, 1회 측정의 차이라 우연일 수도 있다.

### 6. 지표 정의는 도구로 옮기자 고쳐졌다 (v3)

- 질문: Q20 "최근 28일 SKU-029의 일평균 판매량은?", Q16 "SKU-036의 서울센터 결품률은?", Q21 "최근 13주 예측 정확도가 가장 낮은 SKU 4개"
- v1·v2: 정의를 프롬프트에 적어 줘도 `AVG(qty)` 등 자기 방식으로 계산해 틀렸다(사례 3, 4).
- 변경(v3): 지표 계산을 서버의 고정 쿼리로 옮기고, 모델은 도구 이름과 인자만 고르게 했다.
- 결과: 세 문항 모두 맞았다. 기본 세트의 METRIC_DEFINITION 오답이 3건에서 0건이 됐고, 홀드아웃 세트에서도 도구 경로 7문항이 모두 맞았다.

### 7. 대신 도구를 잘못 고른다 (TOOL_SELECTION, v3)

- 질문: Q03 "대구센터 SKU-045의 재주문점은 얼마야?"
- v3 라우터: `reorder_needed(sku=SKU-045, location=대구센터, output=count)` → 결과 `cnt = 0`
- 답변 문장: "대구센터 SKU-045의 재주문점은 0입니다." (숫자 후검증 통과)
- 원인: "재주문점"이라는 낱말을 "재주문 필요" 도구와 연결했다. 같은 식으로 판매량 합계를 일평균 도구로(Q08), 재고 0인 조합을 안전재고 미달 도구로(Q05, Q34) 보냈다. v1에서 맞던 문항이다.
- 변경: 없다. v3을 잰 뒤라 프롬프트를 고치지 않았다. 도구마다 "이 도구가 답하지 않는 질문"을 적거나, 도구 결과의 컬럼이 질문이 묻는 값과 맞는지 한 번 더 확인하는 단계가 다음 후보다.

### 8. 조건이 붙은 지표 질문은 SQL로 보내도 틀린다 (v3)

- 질문: 홀드아웃 Q56 "냉동식품 카테고리의 최근 7일 일평균 판매량은?"
- v3 라우터: sql (카테고리 조건은 도구가 표현하지 못하므로 맞는 선택)
- SQL 단계: `SELECT AVG(qty) ...` (v1과 같은 오답)
- 원인: 도구는 정의가 고정된 질문만 맡는다. 조건이 하나라도 더 붙으면 사례 3의 문제로 돌아간다.

## 레드팀 점검에서 고친 것

v3 코드리뷰에서 고친 것

- **모두 NULL인 결과 행**: MyBatis가 그런 행을 null로 돌려줘 도구 실행기가 예외로 죽었다. 재현 테스트를 쓰고 설정을 고쳤다.
- **기록되지 않는 실패**: 도구 인자 검증 중의 DB 오류와 컬럼 길이를 넘는 도구 이름이 예외로 나가 `chat_log`가 남지 않았다. status로 바꿨다.
- **채점 허점**: 재고보유일수 도구가 재고와 일평균을 함께 돌려줘, 그 값을 묻는 질문에 도구를 잘못 골라도 정답 처리될 수 있었다. 측정 전에 지표 값만 돌려주도록 바꿨다.

v0 ~ v2 레드팀 점검에서 고친 것

- **검증기 우회**: `E'\''`와 `$$` 표기로 문자열 경계를 속이면 시스템 카탈로그 조회, `pg_sleep`, 주석이 검증을 통과했다. 테스트로 재현한 뒤 해당 표기를 거부하고, 함수는 허용 목록 방식으로 바꿨다. `repeat`, `generate_series`, `version`, `current_user`, `nextval` 등이 함께 막힌다.
- **타임아웃 해제**: `scm_ro`의 `statement_timeout`은 세션에서 바꿀 수 있는 기본값이다. DB에서는 막을 수 없어 드라이버 쿼리 타임아웃으로 취소하고, 항상 롤백해 설정이 남지 않게 했다.
- **임시 테이블**: PUBLIC 기본 권한으로 `scm_ro`가 임시 테이블을 만들 수 있었다. 권한을 회수했다.
- **조용한 잘림**: v2의 LIMIT 200으로 결과가 잘려도 `truncated`가 false였다. 검증기가 LIMIT을 적용했고 결과가 상한을 채우면 true로 둔다.
- **모델 장애 시 평가**: Ollama가 꺼진 채 평가하면 정확도 0인 실행이 정상 측정처럼 저장됐다. 중단하고 그 실행을 지운다.
- **시드의 의도하지 않은 결품**: 프로모션 사전 물량이 정기 발주를 밀어 결품이 생겼다. 재고 위치 계산에서 분리했다.

## 한계

- **가짜 데이터, 적은 문항, 1회 측정**이다. 수치는 방향을 보는 용도이며 버전 간 2 ~ 3문항 차이는 우열로 읽지 않는다.
- **v0 점수는 측정일에 따라 달라진다.** v0는 기준일이 없어 15개 문항에서 `CURRENT_DATE`를 썼다. 측정일(2026-11-12 ~ 13)이 데이터 마지막 날과 가까워 Q22, Q23은 맞았지만 다른 날에는 틀릴 수 있다.
- **few-shot 예시가 골든셋과 같은 틀이다.** 질문 문자열은 겹치지 않지만, 안전재고 미달·재고보유일수·어제 판매량 예시는 골든셋 문항과 구조가 같다. 영향을 보려고 예시를 골든셋과 틀이 다른 5개(품목명 조회, 리드타임 조회, 카테고리별 품목 수, 되묻기, 거부)로 바꿔 v1을 다시 재 보았다. 기본 세트는 22 → 20, 심화 세트는 11 → 8이었다(실행 61, 62). 즉 v0 → v1 상승분 15문항 가운데 2문항 정도가 예시의 틀에서 온 것으로 보이며, 나머지는 기준일·기간 규칙·지표 사전의 효과다. 공식 v1 수치(22)는 처음 정한 예시 그대로 둔 값이다. 바꿔 넣은 예시는 `eval/ablation/fewshot_alt.json`에 있고, `prompts/`를 복사해 `fewshot.json`만 이 파일로 바꾼 폴더를 `--chat.prompts-dir`로 주면 다시 잴 수 있다. 이 두 실행의 오답은 원인을 분류하지 않았다.
- **심화 세트는 결과를 본 뒤에 썼다.** 약점을 알고 쓴 문항이라 편향이 있을 수 있다.
- **오답 분류와 교차 검증의 독립성이 약하다.** v1·v2와 심화 세트의 오답 분류, `eval/crosscheck.md`의 재계산은 사람의 손계산이 아니라 생성 SQL과 원본 데이터를 근거로 한 판정이다.
- **추가 컬럼 허용 규칙의 부작용**: 정답이 값 하나인 문항은 생성 결과의 어느 컬럼이든 그 값과 같으면 통과한다.
- **`scm_app`은 컨테이너의 슈퍼유저다**(초기화 단순화). LLM SQL이 쓰는 계정은 `scm_ro`로 분리되어 있다.
- **v2의 스키마 축소는 키워드 규칙**이라 표현이 바뀌면 누락될 수 있다. 키워드가 없으면 전체 스키마로 돌아간다.
- **v2는 느리다.** 프롬프트 토큰은 v1보다 적은데 응답은 1.6배 걸렸다. 질문마다 프롬프트 앞부분이 달라져 모델의 프롬프트 캐시를 재사용하지 못하기 때문으로 추정한다(확인하지 않음).
- RAG, 테넌트 격리, 로그인, 배포는 범위 밖이다.

v3의 한계

- **도구와 라우터는 기본·심화 세트의 결과를 본 뒤에 만들었다.** 두 세트의 v3 점수는 이 점을 감안해 읽는다. 홀드아웃 세트는 구현 전에 동결했지만 v3 범위를 정한 사람이 썼고, 라우터 프롬프트와 예시도 그 문항을 아는 상태에서 썼다. 문자열은 겹치지 않지만(`GoldenSetIT`) 완전히 독립은 아니다.
- **v3은 여러 변경이 한꺼번에 들어간다**(라우터, 도구, 검증·재시도, 답변 문장). 경로별 집계로 나눠 보지만 변경 하나하나의 효과를 분리한 실험은 아니다.
- **라우터 예시의 값이 인자로 새어 들어간다.** 프롬프트의 인자 설명과 예시에 SKU-007, SKU-003을 적었는데, 질문에 SKU가 없는데도 모델이 그 값을 인자로 넣은 호출이 3건 있었다(기본 Q17, 심화 Q38·Q45). 측정 뒤라 고치지 않았다.
- **숫자 후검증은 숫자의 출처만 본다.** 숫자를 엉뚱한 대상에 붙인 문장, 부호가 틀린 문장, 틀린 조회 결과를 옮긴 문장은 걸러내지 못한다. 반대로 모델에게 주지 않은 숫자는 사실이어도 거부한다(재고보유일수 답변의 "28일 기준").
- **자동 분류 TOOL_ARGUMENT에는 도구 선택 오류가 섞여 있다.** 심화 Q38·Q45는 도구로 표현할 수 없는 질문인데, 지원하지 않는 출력 방식을 요청해 거부된 것이라 규칙대로 TOOL_ARGUMENT로 남겼다.
- **채점은 단위에 엄격하다.** v2는 홀드아웃 Q53에서 결품률을 맞게 계산하고도 100을 곱한 백분율로 내서 오답 처리됐다.
- **v3은 느리다.** 질문당 LLM 호출이 2 ~ 4회이고 응답 시간은 v1의 1.5 ~ 2배다.
- **분모가 0인 품목의 순위 제외는 테스트하지 못했다.** 시드 데이터에 최근 28일 판매가 0인 SKU-거점이 없다.
- **v3의 오답 분류와 홀드아웃 문항·정답 SQL도 사람이 손으로 만든 것이 아니다.** 생성 SQL과 도구 호출을 읽고 붙였다.

## 테스트와 CI

- 단위 테스트는 DB와 모델 없이 돈다. 통합 테스트는 `integration` 태그, 그중 모델 호출은 `ollama` 태그로 나눴다.
- GitHub Actions(`.github/workflows/ci.yml`)는 PR과 main 푸시마다 다음을 실행한다.
  - 골든셋 해시 확인, DB 초기화와 시드 검증, 테이블 체크섬 비교
  - 단위 테스트, DB 통합 테스트(Ollama 제외)
  - `oracle` provider로 v0 ~ v3 평가를 돌려 30 / 30인지, 심화·홀드아웃 세트가 20 / 20인지 확인(채점기와 검증기 회귀 방지). oracle의 v3 실행은 SQL 경로만 지나가며, 도구의 정확성은 고정 쿼리 12종을 따로 쓴 참조 SQL과 비교하는 통합 테스트가 본다
  - 프런트 타입 검사, 린트, 빌드
- 실제 모델 측정은 로컬에서만 한다. CI 러너에는 모델이 없다.

## 면접용 1분 설명 (초안, 직접 다듬을 것)

> 한국어 SCM 질문을 SQL로 바꿔 답하는 챗봇을 만들면서, "잘 되는 것 같다"가 아니라 숫자로 말할 수 있게 평가 체계를 먼저 세웠습니다.
> 30문항 골든셋을 측정 전에 해시로 동결하고, 정답을 그대로 넣었을 때 30점이 나오는지로 채점기부터 검증했습니다.
> 스키마만 준 기준선은 30문항 중 7문항이었고, 기준일과 지표 사전을 넣자 22문항이 됐습니다. 오답을 원인별로 나눠 보니 날짜 해석 오류가 9건에서 1건으로 줄어든 것이 가장 컸습니다.
> 반면 SQL 검증과 재시도를 더한 v2는 19문항으로 오히려 낮았고, 지표 계산 오답은 끝까지 남았습니다. 이 결과를 숨기지 않고 한계로 적었습니다.
> 그래서 다음 버전에서는 지표 계산을 서버의 고정 쿼리로 옮기고 모델은 도구와 인자만 고르게 했습니다. 구현 전에 동결한 새 20문항에서 13문항이 16문항이 됐고 지표 오답은 사라졌지만, 재주문점 조회를 "재주문 필요" 도구로 보내는 식의 새 오답이 생겼습니다.
> 답변 문장의 숫자를 조회 결과와 대조하는 후검증도 넣었는데, 통과율 100%가 "문장이 맞다"는 뜻이 아니라는 것을 측정으로 확인했습니다. 틀린 조회를 옮긴 문장도 전부 통과했기 때문입니다.
> 안전 쪽은 읽기 전용 계정, 읽기 전용 트랜잭션, 타임아웃, SQL 검증의 네 겹으로 막았고, 레드팀 점검에서 검증기 우회를 실제로 재현해 고쳤습니다.
