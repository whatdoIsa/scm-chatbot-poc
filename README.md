# SCM 자연어 질의 챗봇 PoC

수요·재고 담당자가 "대구센터 SKU-031은 지금 재고로 며칠 버텨?"처럼 한국어로 물으면 답을 돌려주는 챗봇이다. 로컬 LLM은 답을 내는 방법만 고르고, 조회 실행과 검증은 서버가 읽기 전용 계정으로 한다.

이 저장소에서 가장 중요한 것은 챗봇 화면이 아니라 **정확도를 어떻게 쟀고, 어떤 오답을 보고 무엇을 바꿨으며, 그 결과가 실제로 나아졌는지를 어떻게 확인했는가**다.

| --- | --- |
| 최종 버전 | **v4** (`v4-freeze` 태그) |
| 기준선 → v1 | 기본 30문항 **7 → 22** (날짜 해석 오답 9건 → 1건) |

| 기간·예산 | 2026-11-12 시작, 11-15 마감, 0원 (유료 API 없음) |

## 1. 문제 정의

LLM에게 질문을 SQL로 바꾸게 하면 데모는 금방 된다. 업무에 쓰기 어려운 이유는 두 가지다.

- **틀린 숫자를 그럴듯하게 낸다.** "일평균 판매량"을 정의대로(기간 합 ÷ 일수) 계산하지 않고 `AVG(qty)`로 계산해도 SQL은 오류 없이 실행된다. 이 저장소의 측정에서도 정의를 프롬프트에 적어 준 뒤까지 이 오답이 남았다.
- **모델이 만든 SQL을 그대로 실행하면 위험하다.** 쓰기, 시스템 정보 조회, 오래 걸리는 쿼리를 막아야 한다.

그래서 이 PoC가 확인하려 한 것은 한 문장이다.

> LLM에게는 판단만 맡기고 실행과 검증은 서버가 하도록 설계하면, 같은 작은 모델로도 정확도를 수치로 올릴 수 있고, 그 과정을 측정하고 설명할 수 있다.

예산이 0원이고 노트북 한 대에서 돌려야 해서 모델은 로컬 7B로 고정했다. **더 큰 모델로 바꾸는 대신 시스템 설계로 정확도를 올리는 것**이 과제였다.

## 2. 설계 결정과 이유

| 결정 | 이유 |
| --- | --- |
| 모델은 `sql`·`clarify`(되묻기)·`refuse`(거부) 중 하나를 JSON으로만 낸다 | 모델의 출력 범위를 좁혀야 서버가 검증할 수 있다. 형식은 Ollama의 JSON 스키마 강제로 모든 버전에서 같게 했다 |
| 채점은 SQL 문자열이 아니라 **실행 결과 값**을 정답 SQL의 결과와 비교한다 | 같은 답을 내는 SQL은 여러 가지다. 컬럼명·컬럼 순서는 보지 않고 숫자는 상대 오차 0.1%까지 같게 본다 |
| 평가 문항은 측정 전에 **SHA-256으로 동결**하고, 해시가 다르면 평가 실행기가 시작하지 않는다 | 결과를 보고 문항이나 정답을 고치는 일을 코드로 막는다 |
| 정답을 그대로 돌려주는 `oracle` 모델로 평가하면 만점이 나와야 한다(CI가 매번 확인) | 채점기 버그와 모델 오답을 구분한다 |
| 버전마다 **그 버전을 만들기 전에 동결한 새 문항**으로 비교한다 | 오답을 보고 고친 버전은 그 문항에서 점수가 오르게 마련이다. 본 문항의 점수는 "고칠 수 있다"는 증거일 뿐 성능 추정이 아니다 |
| 오답을 원인별로 분류한다(날짜 해석, 지표 정의, 스키마 오해, 조인·집계, 경로 오선택, 도구 선택, 도구 인자 등 9종) | 다음에 무엇을 바꿀지를 원인에서 고르기 위해서다 |
| 모델·temperature·seed를 모든 버전에서 고정한다 | 버전 간 차이를 프롬프트와 구조의 효과로만 읽기 위해서다 |
| 데이터 접근을 용도에 따라 나눈다 | JPA는 로그·평가 저장, MyBatis는 평가 집계와 정의가 고정된 지표 쿼리, JdbcTemplate은 실행 시점에 정해지는 LLM SQL, PL/pgSQL은 시드 생성에 쓴다 |
| 가짜 데이터는 난수 없이 결정적으로 만든다(6개 테이블, 49,055행, 91일) | 다시 만들어도 체크섬이 같아야 측정을 재현할 수 있다. 결품, 프로모션 급증, 예측 오차가 큰 품목 같은 패턴을 일부러 넣었다 |

## 3. 구조

최종 버전(v4)의 요청 흐름이다. 라우터가 질문을 네 경로 중 하나로 보낸다.

```
질문 ─▶ 라우터(LLM 1회) ─┬─ clarify / refuse ─▶ 되묻기·거부 문장
                         ├─ tool ─▶ 인자 검증 ─▶ MyBatis 고정 쿼리(scm_ro) ──────┐
                         └─ sql  ─▶ SQL 생성(LLM) ─▶ SqlValidator               │
                                    ─▶ 읽기 전용 실행(scm_ro, 오류 시 1회 재시도) ┤
                                                                                  ▼
                       결과 1~20행 ─▶ 답변 문장(LLM 1회) ─▶ 숫자 후검증 ─▶ 응답
```

- **조회 도구 6개**: 일평균 판매량, 재고보유일수, 결품률, 예측 정확도, 안전재고 미달, 재주문 필요. 계산식은 서버의 고정 쿼리에 있고 모델은 도구 이름과 인자(품목, 거점, 기간, 카테고리, 등급, 권역, 출력 방식, 순위 개수)만 고른다. 인자는 검증을 거쳐 바인딩 파라미터로만 들어간다.
- **SQL 경로**: 도구가 표현하지 못하는 질문(단순 조회, 기간 집계, 여러 조건의 조합)을 맡는다. 단일 SELECT, 허용 테이블과 함수, LIMIT 200을 검증한 뒤 실행한다.
- **숫자 후검증**: 답변 문장의 숫자가 조회 결과, 질문, 도구 인자, 날짜, 행 수 중 하나에서 왔는지 확인하고, 출처가 없으면 문장을 버리고 표만 보여 준다.
- 화면(React)은 답변 문장, 결과 표, 근거(SQL 또는 도구 이름과 인자), 기준일과 모델 정보를 보여 준다.

v0~v2는 라우터 없이 SQL 생성 한 단계로 동작하며, 비교를 위해 그대로 남아 있다(`--chat.prompt-version`으로 전환).

### v0 → v1: 모델이 모르는 정보를 준다

- **문제**: "어제 서울센터 판매량"에 모델이 `CURRENT_DATE - 1`을 썼다. 프롬프트에 "오늘"이 없어 실제 시계를 쓴 것이다. 데이터의 마지막 날은 2026-11-08이다. 거점 이름을 ID 자리에 넣는 오답(`location_id = '부산센터'`)도 있었다.
- **변경**: 기준일과 기간 규칙(어제, 최근 N일, 지난주, 지난달 등), 단위 규칙(SKU-7 → SKU-007), 지표 사전, 예시 5개를 넣었다.
- **결과**: 날짜 오답 9 → 1건, 기간 집계 유형 0 / 8 → 7 / 8, 스키마 오해 3 → 0건. 예시가 골든셋과 같은 틀이라는 의심이 있어 틀이 다른 예시로 바꿔 다시 재 보니 22 → 20이었다. 상승분 15문항 중 2문항 정도는 예시의 효과로 본다.

### v1 → v2: 기대와 반대로 나온 결과

- **가설**: 질문에 필요한 테이블만 보여 주고 실행 오류를 다시 묻게 하면 조인·집계 오답이 줄 것이다.
- **결과**: 세 세트 모두 v1보다 1 ~ 3문항 낮았고 응답은 1.6배 느렸다. 실행 오류는 재시도로 일부만 줄었고, 오류 없이 실행되는 잘못된 계산은 재시도 대상이 아니었다.
- **대응**: 프롬프트를 고쳐 점수를 맞추지 않고 결과를 그대로 기록했다. 원인은 확정하지 못했다(문맥이 줄어 되묻기·거부 판단이 약해졌을 가능성). SQL 검증기는 안전장치로서 이후 버전에도 쓴다.

### v1 → v3: 계산을 모델에게서 뺀다

- **문제**: "일평균은 기간 합 ÷ 일수, `AVG(qty)`를 쓰지 않는다"고 적어도 v0 ~ v2 모두 `AVG(qty)`를 썼다. 정의를 문장으로 알려 주는 방식의 한계였다.
- **고려한 방법**: 정의를 더 자세히 적기(v1에서 이미 실패), 재시도(틀린 계산은 오류가 나지 않음), 더 큰 모델(버전 비교가 깨짐), RAG(테이블 6개라 검색할 문서가 없음). 계산식을 서버의 고정 쿼리로 옮기고 모델은 도구와 인자만 고르게 하는 방법을 골랐다. 지표 정의는 회사마다 고정된 것이라 코드에 두는 편이 맞기도 하다.
- **결과**: v3을 만들기 전에 동결한 20문항에서 13 → 16. 도구로 간 지표 질문은 7 / 7 맞았다. 기본 세트에서 끝까지 남던 지표 정의 오답 3건도 모두 맞았다.
- **새로 생긴 오답**: "대구센터 SKU-045의 재주문점은?"을 "재주문 필요" 도구로 보내 개수 0을 가져왔고, 답변 문장은 "재주문점은 0입니다"라고 썼다. 숫자 후검증은 통과했다. 후검증은 숫자의 출처만 볼 뿐 조회가 맞았는지는 보지 못한다는 것을 이 측정에서 확인했다(통과한 문장 54개 중 16개가 오답 조회).

### v3 → v4: 도구를 고르는 기준을 준다

- **문제**: 도구를 잘못 고르는 오답과, "음료 카테고리의 일평균"처럼 조건이 붙어 도구로 답하지 못하고 SQL로 가서 다시 `AVG(qty)`로 틀리는 오답이 남았다.
- **변경**: 도구마다 "이 도구가 답하지 않는 질문"을 적고, 도구에 조건 인자(카테고리, ABC 등급, 권역)를 더했다. 프롬프트의 예시 SKU가 질문에 없는데도 인자로 들어가던 문제는 예시 값을 그 질문에 적힌 값으로만 쓰게 해 막았다(테스트로 확인).
- **프롬프트를 다듬는 방법**: 평가 문항이 아니라 따로 쓴 라우터 개발 세트 41문항을 썼다. 같은 프롬프트로도 결과가 1 ~ 2문항 흔들려 문장을 하나씩 더하며 점수를 쫓지 않고, 후보 5개를 같은 조건에서 비교해 골랐다.
- **결과**: v4를 만들기 전에 동결한 40문항에서 v3 22 → v4 31(새로 맞힘 10, 새로 틀림 1, p = 0.012). 다만 이 세트에는 v4에서만 도구로 답할 수 있는 조건 문항 7개가 있다. 이를 빼면 20 / 33 → 24 / 33(p = 0.22)이라 그 밖의 개선은 우연과 구분되지 않는다.

### v4 → v5: 시도했지만 채택하지 않았다

- **문제**: v4가 "출고량"·"판매량 합계" 질문을 일평균 도구로 보냈다. 프롬프트에 "합계에는 쓰지 않는다"고 적어 두어도 막히지 않았다.
- **변경**: 프롬프트는 문장 하나를 바꿀 때마다 다른 문항이 흔들려서, 서버가 도구 호출을 질문의 낱말과 대조하는 결정적 규칙을 더했다. 질문에 그 지표의 낱말이 없으면 SQL 단계로 넘기고, 순위 방향을 질문의 낱말에 맞춘다.
- **결과**: 규칙을 쓰기 전에 오답을 본 110문항에서는 85 → 94, 새로 틀린 문항이 없었다. 그러나 규칙을 보지 않은 사람이 새로 쓴 40문항에서는 29 → 28이었다. "며칠 버텨", "발주를 넣어야" 같은 말바꿈을 "지표 낱말이 없다"고 읽어 v4가 도구로 맞히던 문항을 SQL로 넘겼다.
- **결정**: 본 문항에서의 개선이 처음 보는 문항에서 재현되지 않아 채택하지 않았다. 새 세트를 본 뒤 규칙을 고치면 그 세트도 본 세트가 되므로 고치지 않았다. 코드와 측정은 비교 기록으로 남겼다.

| --- | --- | --- | --- | --- | --- | --- |
| 기본 30문항 (v0 전에 동결) | 7 | 22 | 19 | 23 | 22 | 28 |
| 심화 20문항 (v0 ~ v2 결과를 본 뒤 작성) | 5 | 11 | 9 | 11 | 14 | 14 |
| 홀드아웃 20문항 (v3 전에 동결) | 3 | 13 | 11 | **16** | 18 | 19 |
| v4 세트 40문항 (v4 전에 동결) | - | 21 | 21 | 22 | **31** | 33 |
| v5 세트 40문항 (v5 규칙을 보지 않고 작성) | - | - | - | - | **29** | **28** |

굵은 칸은 버전을 채택할지 정할 때 근거로 쓴 값이다. 모두 그 버전을 만들기 전에 동결한 세트에서 쟀다. 읽는 법은 다음과 같다.

- **세트의 오답을 보고 만든 버전의 점수는 부풀어 있다.** 예를 들어 기본 세트의 v4·v5 점수는 그 세트의 오답을 보고 고친 결과라 성능 추정이 아니다. v5가 위 네 줄에서 가장 높지만 마지막 줄에서 v4보다 낮은 것이 그 예다.
- **2 ~ 3문항 차이는 우열로 읽지 않는다.** 문항 수가 적고 각 1회 측정이다. 그래서 짝 비교(같은 문항에서 새로 맞힘·새로 틀림)와 부호 검정을 함께 봤다.
- 응답 시간은 v1이 질문당 4.5 ~ 6.7초, v3·v4는 LLM 호출이 평균 2.1 ~ 2.5회로 늘어 6 ~ 12초다.

유형별 정확도, 경로별 정확도, 오답 원인 분류표, 오답 사례 10건은 [docs/RESULTS.md](docs/RESULTS.md)에 있다.

## 6. 남은 개선점

v4가 처음 보는 40문항에서 틀린 11문항은 다음과 같다.

| 묶음 | 문항 수 | 내용 |
| --- | --- | --- |
| 되묻기 | 3 / 3 모두 틀림 | "세제 재고 얼마나 있어?"(세제가 두 품목), "SKU-030 수량 얼마야?"(재고·판매·예측 중 무엇인지 없음), "그 SKU 결품률 다시 보여줘"(가리키는 품목 없음)에 되묻지 않고 하나를 골라 답했다 |
| 도구 선택·인자 | 4 | "9월 한 달 일평균"을 최근 30일 도구로, "센터별 결품률"에 순위 개수 없음, "긴 쪽으로"를 오름차순으로(2건) |
| SQL 단계·거부 | 4 | "9월"을 2023년으로 해석, 두 지표 비교(재고보유일수 < 리드타임) 계산 오류, 주 단위 집계 실행 오류, 원가 조회를 거부 |

다음 후보는 아래와 같다. 모두 아직 검증하지 않은 가설이다.

- **되묻기 판단을 따로 둔다.** 지금은 라우터가 경로와 함께 판단해서, 해석이 여러 개인 질문에도 그중 하나를 골라 답한다. 대상 품목, 수량의 종류, 기간이 하나로 정해지는지를 먼저 확인하는 단계가 후보다.
- **낱말 규칙 대신 근거를 대조한다.** v5에서 낱말 규칙은 처음 보는 표현에 약했다. 라우터가 인자마다 질문의 근거 구절을 함께 내고 서버가 그 구절이 질문에 있는지 확인하는 방식을 시험해 볼 수 있다.
- **지표끼리 비교하는 질문을 도구 결과의 조합으로 푼다.** 지표 하나는 도구로 맞히지만 두 지표를 비교하면 SQL로 가서 다시 계산을 틀린다.
- **평가를 키운다.** 문항 수를 늘리고, 반복 측정하고, 구현자와 다른 사람이 문항을 쓰게 한다. v5 비교 세트는 구현을 보지 않은 별도 에이전트가 썼고 사람이 검토했다.

## 7. 안전장치와 점검

LLM이 만든 SQL은 아래 네 겹을 모두 지나야 실행된다.

1. **DB 권한**: 실행 계정 `scm_ro`는 `scm` 스키마 6개 테이블의 SELECT 권한만 있다. 로그·평가 테이블(`app` 스키마)과 임시 테이블 생성 권한은 없다.
2. **읽기 전용 트랜잭션**: 실행 후 항상 롤백해 SQL이 세션 설정을 바꿔도 커넥션에 남지 않는다.
3. **드라이버 타임아웃 5초, 최대 1,000행**: SQL이 `statement_timeout`을 풀어도 드라이버가 취소한다.
4. **SQL 검증기**(v2부터): 단일 SELECT, 허용 테이블, 허용 함수 목록, LIMIT 200.

직접 공격해 본 뒤 고친 것

- `E'\''`, `$$` 표기와 큰따옴표 식별자 안의 작은따옴표로 문자열 경계를 속여 시스템 카탈로그 조회와 `pg_sleep`이 검증을 통과하는 것을 재현했다. 문자열과 식별자를 따로 읽는 스캐너와 함수 허용 목록으로 바꿨다.
- `scm_ro`가 PUBLIC 기본 권한으로 임시 테이블을 만들 수 있었다. 권한을 회수했다.
- LIMIT으로 결과가 잘려도 응답에 표시되지 않았고, Ollama가 꺼진 채 평가하면 정확도 0인 실행이 정상 측정처럼 저장됐다. 둘 다 고쳤다.
- 도구가 재고와 일평균을 함께 돌려줘서, 도구를 잘못 골라도 채점의 "추가 컬럼 허용" 규칙 때문에 정답 처리될 수 있었다. 측정 전에 지표 값만 돌려주게 바꿨다.

## 8. 한계

- **가짜 데이터, 적은 문항(30 ~ 40), 버전별 1회 측정**이다. 수치는 방향을 보는 용도다.
- **세트의 독립성이 완전하지 않다.** 홀드아웃과 v4 세트는 구현 전에 동결했지만 그 버전의 범위를 정한 사람이 썼다. v4 세트의 조건 문항 7개는 v4에 유리한 구성이다.
- **버전마다 변경 여러 개가 한꺼번에 들어갔다.** 변경 하나하나의 효과를 나눈 실험은 아니다.
- **숫자 후검증 통과율 100%는 "답이 맞다"는 뜻이 아니다.** 출처 없는 숫자를 찾지 못했다는 뜻이며 틀린 조회를 옮긴 문장도 통과한다.
- **v3 이후는 느리다.** 질문당 LLM 호출이 1 ~ 4회라 v1보다 1.1 ~ 1.7배 걸린다.
- RAG, 로그인, 테넌트 격리, 배포는 범위 밖이다.

버전별 한계 전체는 [docs/RESULTS.md](docs/RESULTS.md#한계)에 있다.

## 9. 실행 방법

필요한 것: Java 21, Docker(Compose), Ollama와 `qwen2.5-coder:7b`, Node 22. 모든 명령은 저장소 루트에서 실행한다.

```bash
cp .env.example .env            # change-me 값을 바꾼다
set -a; . ./.env; set +a
bash scripts/db_reset.sh        # Postgres 컨테이너 + 스키마 + 시드
bash scripts/verify_db.sh       # 시드 검증 23개 항목
bash scripts/eval_restore.sh    # (선택) 저장된 측정 결과를 DB에 넣는다
```

백엔드와 화면은 터미널을 따로 열어 실행한다.

```bash
# 터미널 1: 백엔드 http://localhost:8080 (최종 버전 v4)
set -a; . ./.env; set +a
(cd backend && ./gradlew bootRun --args='--chat.llm.provider=ollama --chat.prompt-version=v4')
```

```bash
# 터미널 2: 화면 http://localhost:5173
(cd frontend && npm ci && npm run dev)
```

`--chat.llm.provider`를 주지 않으면 모델 없이 동작하는 `fake`가 쓰인다. 프롬프트 버전은 `--chat.prompt-version=v0|v1|v2|v3|v4|v5`로 바꾼다(기본 v1).

평가 실행

```bash
(cd backend && ./gradlew bootRun --args='--spring.profiles.active=eval --chat.llm.provider=ollama --eval.versions=v1,v4')
```

평가 실행기는 골든셋의 해시가 `eval/golden_set.sha256`과 다르면 시작하지 않는다. 다른 세트는 `--eval.golden-path=../eval/golden_set_v4.json --eval.golden-hash-path=../eval/golden_set_v4.sha256`처럼 파일과 해시를 함께 준다. 결과는 `eval/reports/`에 마크다운으로 남는다.

## 10. 테스트와 CI

```bash
(cd backend && ./gradlew test)                  # 단위 테스트 (DB, 모델 불필요)
(cd backend && ./gradlew integrationTest)       # 통합 테스트 (DB, Ollama 필요)
bash scripts/final_check.sh                     # 전체 점검
```

GitHub Actions(`.github/workflows/ci.yml`)가 PR과 main 푸시마다 실행하는 것

- 다섯 평가 세트의 해시 확인, DB 초기화와 시드 검증, 테이블 체크섬 비교
- 단위 테스트, DB 통합 테스트(모델 호출 제외)
- `oracle`로 모든 버전과 세트를 평가해 만점인지 확인(채점기와 검증기 회귀 방지)
- 프런트 타입 검사, 린트, 빌드

실제 모델 측정은 로컬에서만 한다. 동결한 v3 라우터 프롬프트는 해시로 테스트에 고정해 이후 공용 코드를 고쳐도 측정 조건이 바뀌지 않았음을 확인한다.
