## 1. 목적과 사용자

- 목적: 한국어 질문을 LLM이 SQL·되묻기·거부 중 하나로 바꾸고, 서버가 검증·읽기 전용 실행해 결과를 돌려주는 챗봇. 핵심 산출물은 챗봇이 아니라 골든셋 정확도 측정과 v0 → v2 개선 비교다.
- 사용자(가정): 수요·재고 계획 담당자. 기준일(as_of_date)은 데이터의 마지막 날 2026-11-08(일).
- 환경: MacBook Air M2 24GB 한 대, 전부 로컬 실행, 유료 서비스 없음.
- 성공 정의: 결과표(v0, v1, v2 × 유형별 정확도), 오답 원인 분류표, 원인별 개선 3건 이상이 README에 채워진다. 목표 수치는 두지 않는다.

## 5. 도메인 규칙 (골든셋, 지표 사전, 프롬프트가 모두 따르는 단일 기준)

### 5.1 기간 해석 (기준일 2026-11-08, 일요일, 주는 월~일)

| 표현 | 해석 |
| --- | --- |
| 오늘, 현재 | 2026-11-08 (재고는 이 날의 스냅샷) |
| 어제 | 2026-11-07 |
| 최근 N일 | 기준일−N+1 ~ 기준일 (예: 최근 7일 = 11-02 ~ 11-08) |
| 이번 주 | 2026-11-02 ~ 2026-11-08 |
| 지난주 | 기준일이 속한 주의 직전 주: 2026-10-26 ~ 2026-11-01 |
| 이번 달 | 2026-11-01 ~ 2026-11-08 |
| 지난달 | 2026-10-01 ~ 2026-10-31 |
| 최근 13주 | forecast_weekly.week_start 2026-08-10 ~ 2026-11-02 전체 |
| 데이터 범위 밖 기간 | refuse (데이터는 2026-08-10 ~ 2026-11-08만 존재) |

### 5.2 단위 규칙

- "품목", "SKU"로 묻거나 단위를 말하지 않으면 SKU 단위(전 거점 합산)로 집계한다.
- "SKU-거점", "거점별"로 묻거나 특정 거점을 말하면 SKU×거점 단위로 집계한다.
- SKU 표기는 `SKU-007` 형식이며 "SKU-7"은 `SKU-007`로 정규화한다.

### 5.3 지표 정의

| 지표 | 정의 |
| --- | --- |
| 일평균 판매량(최근 N일) | 대상 범위의 최근 N일 qty 합 ÷ N |
| 재고보유일수 | 기준일 on_hand ÷ (최근 28일 qty 합 ÷ 28). 분모가 0이면 NULL로 두고 순위·집계에서 제외. SKU 단위는 분자·분모 모두 거점 합산 |
| 결품률 | 기간 내 on_hand=0인 (SKU, 거점, 일) 수 ÷ 기간 내 전체 (SKU, 거점, 일) 수. 기간 미지정이면 전체 데이터 기간 |
| 안전재고 미달 | 기준일 on_hand < safety_stock |
| 재주문 필요 | 기준일 on_hand + in_transit ≤ reorder_point |
| 예측 정확도 | 1 − WMAPE. WMAPE = Σ\|실적−예측\| ÷ Σ실적, 실적은 week_start ~ +6일 qty 합, 기본 집계 단위는 SKU(전 거점, 13주) |

### 5.4 채점 규칙

- sql 문항: 생성 SQL 실행 결과와 정답 SQL 실행 결과를 값 기준으로 비교한다. 컬럼명은 무시한다.
- 추가 컬럼 허용: 정답 SQL은 판정에 필요한 최소 컬럼만 반환한다. 정답의 각 컬럼이 생성 결과의 서로 다른 컬럼 하나와 값이 모두 일치하면(컬럼 순서 무관) 정답이다. 생성 결과에 라벨 컬럼(sku, 거점명 등)이 더 있어도 된다. 행 수는 같아야 한다.
- 숫자는 상대 오차 0.1% 이내(정답이 0이면 절대 오차 1e-9 이내)를 같은 값으로 본다.
- 행 순서는 `orderSensitive=true`인 문항(비교·순위)만 비교한다. 그 외는 행 순서를 무시한다.
- 정답 SQL 결과는 200행 이하여야 한다(v2의 LIMIT 200과 비교 조건을 같게 하기 위함).
- clarify 문항은 action=clarify, refuse 문항은 action=refuse면 정답이다.
- 오답 원인 `error_type`: SCHEMA_MISUNDERSTANDING, METRIC_DEFINITION, DATE_RANGE, JOIN_AGGREGATION, ACTION_MISMATCH, FORMAT_ERROR, SQL_EXECUTION_ERROR. 자동 기록은 SQL_EXECUTION_ERROR, ACTION_MISMATCH, FORMAT_ERROR만 하고, 나머지는 NULL(미분류)로 저장한 뒤 사람이 SQL로 갱신한다.

### 5.5 데이터 요구사항

- 50 SKU × 5 거점(서울센터, 부산센터, 대전센터, 광주센터, 대구센터) × 91일.
- 시드에 심을 패턴과 검증 하한(제안값, 생성 후 `verify.sql`에 고정): 결품 구간이 있는 SKU-거점 3쌍 이상, 안전재고 미달 3쌍 이상 30쌍 이하, 재주문 필요 3쌍 이상, WMAPE 0.4 초과 SKU 3개 이상, 프로모션 급증 SKU 3개 이상(최대/평균 판매량 ≥ 3), on_hand < 0 없음.

## 6. 범위 밖

기획서 2장 "제외하는 것"을 따른다. RAG(pgvector), 테넌트 격리(RLS), QueryDSL, 로그인, 배포는 구현하지 않는다. 조회 도구 호출, 라우터 분리, 결과 문장 생성, 숫자 후검증은 v0~v2에서는 구현하지 않고 v3 경로(10장)에서만 구현한다.

## 7. 알려진 단순화 (README 한계 항목에 옮긴다)

- 가짜 데이터, 30문항, 반복 1회이므로 방향 확인이다.
- `scm_app`은 컨테이너의 슈퍼유저다(초기화 단순화). LLM SQL이 쓰는 계정은 `scm_ro`로 분리되어 있다.
- v2의 스키마 축소는 키워드 규칙이라 표현이 바뀌면 누락될 수 있다. 키워드가 없으면 전체 스키마로 폴백한다.

## 10. v3 확장 (poc-freeze 이후, 2026-11-13 확정)

v0~v2의 프롬프트, 동작, 측정 결과는 `poc-freeze` 태그 그대로 둔다. v3은 새 경로로 더하며, 1~9장과 충돌하면 이 장이 우선한다. 모델과 설정(`qwen2.5-coder:7b`, temperature 0, seed 42, num_ctx 8192)은 바꾸지 않는다.

### 10.1 목적과 가설

v1·v2 측정에서 남은 문제는 두 가지다. 지표 정의를 문장으로 알려 줘도 모델이 자기 방식으로 계산한다(일평균에 `AVG(qty)`, 결품률, 예측 정확도). 그리고 결과를 사람에게 문장으로 전하는 단계가 없다.

| 변경 | 확인하려는 가설 |
| --- | --- |
| 라우터 분리 | 질문과 무관하게 고정된 짧은 프롬프트로 경로(도구·SQL·되묻기·거부)만 먼저 고르면, 되묻기·거부 판단과 도구 선택이 SQL 생성과 섞이지 않는다 |
| 조회 도구 호출 | 지표 계산을 서버의 고정 쿼리로 옮기면 지표 정의 오답이 줄어든다. 대신 도구가 표현하지 못하는 질문을 도구로 보내는 새 오답이 생길 수 있다 |
| 답변 문장 + 숫자 후검증 | 모델이 결과를 문장으로 옮길 때 숫자를 바꾸거나 새로 계산하는 일이 얼마나 있는지 측정하고, 그런 문장은 사용자에게 내보내지 않는다 |

목표 수치는 두지 않는다. v3이 v1보다 낮게 나와도 그대로 기록한다.

### 10.2 처리 흐름

```
질문 ─▶ 라우터(LLM 1회) ─┬─ clarify / refuse ─▶ message
                         ├─ tool ─▶ 인자 검증 ─▶ MyBatis 고정 쿼리(scm_ro) ─┐
                         └─ sql  ─▶ v1 프롬프트로 SQL 생성(LLM 1회)          │
                                    ─▶ SqlValidator ─▶ 읽기 전용 실행         │
                                       (실행 오류 시 1회 재시도) ────────────┤
                                                                             ▼
                        결과 1~20행 ─▶ 답변 문장(LLM 1회) ─▶ 숫자 후검증 ─▶ 응답
```

- 라우터가 sql을 골랐는데 SQL 생성 단계가 clarify·refuse를 내면 그 action을 최종 결과로 한다.
- 도구 인자 검증에 실패하면 `TOOL_REJECTED`로 끝낸다. SQL 경로로 넘기거나 다시 묻지 않는다(v2의 `SQL_REJECTED`와 같은 원칙이며, 라우터의 인자 오류를 그대로 측정하기 위함).
- 답변 문장 단계의 실패(LLM 장애, 형식 오류, 검증 실패)는 조회 결과를 버리지 않는다. 표는 그대로 응답하고 문장만 뺀다.

### 10.4 조회 도구 규칙

도구는 5.3의 지표 정의를 그대로 옮긴 것이고, 골든셋 문항에 맞춘 변형(카테고리·등급·권역 조건, 임계값 조건 등)은 넣지 않는다. 도구가 표현하지 못하는 질문은 SQL 경로가 맡는다.

| 도구 | 지표(5.3) | 전용 인자 | 출력 방식 |
| --- | --- | --- | --- |
| `avg_daily_sales` | 일평균 판매량(최근 N일) | `days` 1~91 필수 | value, ranking |
| `days_of_supply` | 재고보유일수 | 없음 | value, ranking |
| `stockout_rate` | 결품률 | `start_date`, `end_date` 선택(없으면 전체 데이터 기간) | value, ranking |
| `forecast_accuracy` | 예측 정확도(13주) | 없음 | value, ranking |
| `below_safety_stock` | 안전재고 미달 | 없음 | list, count |
| `reorder_needed` | 재주문 필요 | 없음 | list, count |

- 공통 인자: `sku`(선택), `location`(선택, 거점 이름). 5.2 단위 규칙을 따른다. 거점이 없으면 전 거점 합산, 있으면 그 거점만 본다.
- value: 인자가 가리키는 범위 전체를 하나로 집계한 1행.
- ranking: SKU 단위 순위. `top_n` 1~50, `order` asc·desc 필수이고 `sku`는 비워야 한다. 값이 NULL인 품목(분모 0)은 제외하고 동점은 sku 오름차순으로 푼다.
- list: 조건을 만족하는 SKU-거점 행(sku, 거점 이름 오름차순). count: 그 개수 1행.
- 기간이 달력 구간인 일평균("9월 일평균"), SKU-거점 단위 순위, 거점·카테고리 단위 순위는 도구가 지원하지 않는다.

### 10.5 숫자 후검증 규칙

답변 문장에서 숫자 토큰(쉼표와 소수점을 포함한 아라비아 숫자, 뒤따르는 `%`)을 모두 뽑는다. 전각 숫자는 반각으로 바꿔 읽는다. `SKU-007`, `LOC-01` 같은 식별자 안의 숫자는 수량이 아니므로 문장에서도, 허용 집합을 만드는 질문과 문자열 셀에서도 뽑지 않는다(식별자는 `SKU-`, `LOC-`로 시작하는 것만이다). 토큰 하나가 아래 중 하나에 해당하면 허용이고, 허용되지 않은 토큰이 하나라도 있으면 `REJECTED`다.

| 허용 근거 | 규칙 |
| --- | --- |
| 결과 셀 | 숫자 셀 값을 토큰의 소수 자릿수에 맞춰 반올림하거나 버린 값과 같다. 예: 셀 14.7187이면 14.7, 14.72, 15, 14는 허용, 14.8과 16은 불허 |
| 백분율 | `%`나 "퍼센트"가 붙은 토큰은 셀 값 × 100과 같은 규칙으로도 비교. 붙지 않은 토큰은 × 100과 비교하지 않는다 |
| 질문과 인자 | 질문 문장에 나온 숫자, 도구 인자의 숫자(`days`, `top_n`) |
| 문자열 셀 | 결과의 문자열 셀에 적힌 숫자(품목명 "냉동만두 1kg"의 1처럼 이름을 옮겨 적은 경우) |
| 날짜 | 기준일, 도구 인자의 날짜, 결과의 날짜 셀을 이루는 연·월·일 숫자 |
| 행 수와 순위 | 결과 행 수, 1부터 결과 행 수까지의 정수 |

- 문장에 숫자가 하나도 없으면 `VERIFIED`다(검증할 것이 없음).
- 한글 수사("삼십 개")와 단위 환산("1.2천 개")은 다루지 않는다. 환산한 숫자는 대개 결과 셀과 맞지 않아 `REJECTED`가 되지만, 우연히 허용 집합의 숫자와 같으면 통과한다.
- 행 수·순위(1부터 행 수까지)와 기준일의 연·월·일은 어떤 수량으로 쓰여도 통과한다. 결과가 1행이어도 "약 1억 원"의 1, 기준일이 11월 8일이면 "11개"의 11이 통과한다.
- 점으로 쓴 날짜(2026.09.21)는 소수로 읽혀 거부된다.
- 후검증은 숫자의 출처만 본다. 숫자를 엉뚱한 대상에 붙인 문장("A가 120개"인데 120은 B의 값)은 걸러내지 못한다. 부호도 보지 않는다(절댓값으로 비교).
- 모델에게 주지 않은 숫자는 사실이어도 거부한다. 예를 들어 재고보유일수 답변에 "최근 28일 기준"이라고 쓰면 28은 질문에도 결과에도 없어 `REJECTED`다.

### 10.6 채점·평가 추가 규칙

- 5.4의 채점은 그대로다. 정답이 sql인 문항은 action이 `sql`이든 `tool`이든 실행 결과를 정답 SQL 결과와 비교한다.
- 답변 문장의 내용은 정답 여부에 반영하지 않는다. 숫자 검증 통과율 = `VERIFIED` ÷ (`VERIFIED` + `REJECTED`)만 따로 기록한다.
- 오답 원인 추가: `TOOL_SELECTION`(도구가 표현할 수 없는 질문을 도구로 보냈거나 다른 도구를 고름), `TOOL_ARGUMENT`(도구는 맞고 인자가 틀림). 정답이 sql인 문항의 `TOOL_REJECTED`는 `TOOL_ARGUMENT`로 자동 기록하고, 나머지는 5.4와 같이 사람이 붙인다. 정답이 clarify·refuse인 문항에 도구로 답한 것은 인자 검증 결과와 무관하게 `ACTION_MISMATCH`다.
- 도구는 자기 지표 값만 돌려준다. 구성 요소(재고, 일평균)를 함께 내면 5.4의 추가 컬럼 허용 규칙 때문에 잘못 고른 도구가 정답으로 채점될 수 있다.
- 평가 실행에는 경로(route)별 문항 수와 정답 수를 함께 남긴다.

### 10.7 홀드아웃 세트

도구와 라우터는 기본·심화 세트의 결과를 본 뒤에 설계했다. 이 편향을 줄이려고 `eval/golden_set_v3.json` 20문항(Q51~Q70)을 따로 둔다.

- 라우터 프롬프트, `tools.yml`, 라우터 예시를 쓰기 전에(T12) 문항을 확정하고 `eval/golden_set_v3.sha256`으로 동결한다. 이후 문항과 정답 SQL은 바꾸지 않는다.
- 구성: SIMPLE_LOOKUP 2, PERIOD_AGG 3, METRIC 7, RANKING 4, AMBIGUOUS 2, REFUSE 2. 도구로 답할 수 있는 지표 질문 8개(지표 이름을 쓰지 않은 표현 포함), 지표처럼 보이지만 도구가 표현하지 못하는 질문 3개, 일반 조회·집계 6개, 되묻기·거부 3개.
- 질문은 발주 검토, 결품 리뷰, 예측 성능 리뷰, 판매 추이 점검 같은 업무 장면에서 쓰는 표현으로 썼다(DOS, 출고량, 전월, 전일, 당월 누계, 워스트 N, 발주). 지표 사전에 없는 말이 섞여 있어 사전의 키워드에 기대는 정도도 함께 드러난다.
- v0~v3 네 버전을 모두 이 세트로 잰다. 라우터 예시와 few-shot의 질문은 세 골든셋 어느 문항과도 겹치지 않아야 한다.

### 10.8 알려진 단순화 (README 한계에 옮긴다)

- 도구 6개와 라우터 예시는 기본·심화 세트를 본 뒤에 만들었다. 두 세트의 v3 점수는 이 점을 감안해 읽고, 홀드아웃 세트를 함께 본다. 홀드아웃 세트도 v3 범위를 정한 뒤에 썼으므로 완전히 독립은 아니다.

- 질문당 LLM 호출이 최대 4회라 v1보다 느리다.
- 숫자 후검증은 숫자의 출처만 확인한다(10.5).

### 11.3 조건 인자 규칙

- `category`는 product.category, `abc_class`는 A·B·C, `region`은 location.region의 값이어야 한다. 셋 다 선택이다.
- `location`과 `region`은 함께 줄 수 없다. `sku`와 `category`·`abc_class`도 함께 줄 수 없다(품목 하나에 품목 조건을 거는 것은 뜻이 없다).
- value는 조건에 맞는 범위 전체를 하나로 집계한다. ranking은 조건에 맞는 품목 안에서의 SKU 순위다. list·count는 조건에 맞는 SKU-거점만 센다.
- 여전히 도구가 표현하지 못하는 것: 지표 값에 대한 조건(임계값, 다른 값과의 비교), 두 기간의 비교, 거점·카테고리 단위 순위, 달력 구간의 일평균.

### 11.4 평가

- 새 세트 `eval/golden_set_v4.json` 40문항(Q71~Q110)을 v4의 프롬프트·도구·예시를 쓰기 전에 `eval/golden_set_v4.sha256`으로 동결한다. 구성: SIMPLE_LOOKUP 7, PERIOD_AGG 7, METRIC 12, RANKING 7, AMBIGUOUS 3, REFUSE 4.
- 문항의 의도: v3 도구로 답할 수 있는 지표 질문 7, 조건이 붙어 v4에서만 도구로 답할 수 있는 질문 7, v4 도구로도 표현할 수 없는 지표 질문 3, 도구의 낱말과 겹치지만 도구가 답하지 않는 조회(안전재고 값, 재주문점, 예측 수량, 판매량 합계) 4, 일반 조회·집계 12, 되묻기·거부 7.
- 네 세트 110문항에서 v3과 v4의 문항별 정오를 짝지어 본다. 새로 맞힌 문항 수와 새로 틀린 문항 수를 함께 보고하고 부호 검정의 p값을 적는다. 구간 추정이 넓다는 점을 숨기지 않는다.

### 11.5 알려진 단순화

- v4의 변경은 기존 세 세트(70문항)의 v3 오답을 본 뒤에 정했다. 세 세트의 v4 점수는 그 문항들에 맞춘 결과로 읽어야 하고, 깨끗한 비교는 새 세트 40문항뿐이다.
- 새 세트도 v4의 범위를 정한 사람이 썼다. 조건이 붙은 지표 질문을 7개 넣은 것은 v4에 유리한 구성이다. 이 7문항을 뺀 점수를 함께 보고한다.
- 40문항이어도 신뢰구간은 넓다(80%일 때 대략 ±12%p).
- 새 세트의 v1~v3은 FR-24로 고친 검증기로 잰다. `v3-freeze`의 검증기라면 한 글자 리터럴이 든 문항(Q77, Q96)이 v2·v3에서 거부된다. 이 예외만 v3 동작의 변경으로 둔다.
- v4도 변경 세 가지가 한꺼번에 들어간다.

## 12. v5 (v4-freeze 이후, 2026-11-14 제안, 사용자 확인 전)

v0~v4의 프롬프트, 도구, 동작, 측정 결과는 그대로 둔다. v5는 v4의 라우터(프롬프트, 도구 목록, 예시, 출력 형식)를 한 글자도 바꾸지 않고, 서버가 라우터의 도구 호출을 질문과 대조하는 점검 하나만 더한다. 그래서 v4 → v5의 차이는 점검의 효과만이다. 모델과 설정은 그대로다.

### 12.1 목적

v4 측정에서 남은 도구 경로 오답은 프롬프트에 "이 도구는 이런 질문에 쓰지 않는다"고 적어 둔 유형이었다(합계·출고량을 일평균 도구로, 예측 수량을 예측 정확도로, 거점 순위를 품목 순위로, "가장 긴"을 asc로). 라우터 개발 세트에서는 프롬프트 문장을 하나 바꿀 때마다 다른 문항이 1~2개씩 흔들려 프롬프트로는 더 줄이기 어려웠다. v5는 이 판단을 서버의 결정적 규칙으로 옮긴다.

### 12.2 처리 흐름

v4와 같다(10.2). 도구 경로만 다음과 같이 바뀐다.

```
라우터 tool ─▶ 인자 검증 ─실패─▶ SQL 단계(v1 프롬프트, 검증, 재시도)
                 │ 통과
                 ▼
             도구 경로 점검(ToolRouteGuard) ─맞지 않음─▶ SQL 단계
                 │ 맞음(정렬 방향을 고쳤을 수 있음)
                 ▼
             고정 쿼리 실행
```

- v4까지는 인자 검증 실패를 `TOOL_REJECTED`로 끝냈다(라우터 오류를 그대로 재려고). v5는 정확도가 목표이므로 SQL 단계로 넘긴다.
- SQL 단계로 넘긴 경우 route는 `sql`이고, `tool_name`·`tool_args`에 라우터가 냈던 도구와 인자, 그리고 `guard`(넘긴 이유)를 남긴다. 응답의 `tool`은 null이다.

### 12.3 점검 규칙

판단은 공백을 지우고 소문자로 바꾸고 거점 이름(`location.name`)을 지운 질문에서 한다. 거점 이름 속의 "센터"를 거점 순위로 읽지 않기 위해서다. 위에서부터 처음 걸리는 규칙을 쓴다.

| 규칙 | 내용 | 결과 |
| --- | --- | --- |
| 지표 낱말 | 도구의 지표를 가리키는 낱말이 질문에 없다. 일평균: 일평균·하루 평균·"평균 판매/출고", 재고보유일수: 재고보유일수·재고일수·DOS 등, 결품률: 결품률·결품 비율 등, 예측 정확도: 정확도·잘 맞·"예측 … 오차/안 맞" 등(WMAPE·오차율만 쓴 질문은 오차를 묻는 것이라 제외), 안전재고 미달: "안전재고"와 미달·밑돌·못 미치 등, 재주문 필요: "재주문/발주"와 필요·해야·대상 | SQL 단계 |
| 다른 컬럼 조건 | 안전재고 미달에 리드타임·재주문점·입고 예정, 재주문 필요에 리드타임·안전재고가 함께 나온다 | SQL 단계 |
| 지표 값 조건 | 값·순위 도구 질문에 "3일 미만", "보다 짧은", "넘는" 등 지표 값의 조건이 있다 | SQL 단계 |
| 묶음 | 거점·센터·권역·카테고리 + "별" | SQL 단계 |
| 거점·카테고리 고르기 | 질문이 품목이 아니라 거점·센터·창고·권역·지역·카테고리를 고른다("어느 센터", "가장 … 센터는?", "상위 3개 센터", "카테고리 중 … 가장", "권역 순으로"). 출력 방식과 무관 | SQL 단계 |
| 정렬 방향 | ranking이고 질문에 한쪽 방향의 낱말만 있다(가장 높/많/긴/잘, 상위 ↔ 가장 낮/적/짧/못/잘 안, 하위). 예측 정확도에서 방향 낱말이 "오차·틀린·빗나"를 꾸미면(오차가 가장 큰) 방향을 뒤집는다 | 방향을 고쳐 실행 |

### 12.4 평가

- v5의 규칙은 v4의 네 세트 110문항 오답을 본 뒤에 썼다. 네 세트 모두 v5에는 본 세트이며, 그 점수는 맞춘 결과로 읽는다.
- 라우터 개발 세트 2(36문항, `backend/src/test/resources/router_dev2_v5.json`)는 규칙보다 먼저 썼고, 처음 규칙을 고정할 때까지 이 세트의 모델 출력을 보지 않았다. 그러나 규칙을 쓰는 동안 질문은 보였고 일부 질문을 단위 테스트에 그대로 옮겼다(코드리뷰에서 지적, 이후 테스트에서 뺌). 같은 커밋에 들어가 이력으로 순서를 보일 수도 없다. 기대가 sql·clarify·refuse인 24문항에서는 점검의 구조상 v5가 v4보다 나빠질 수 없어, 의미 있는 비교는 도구 문항 12개뿐이다. 약한 근거다.
- 첫 측정(실행 293~296) 뒤 코드리뷰가 규칙의 오판(거점 이름 속 "센터", "가장 잘 안 팔리는", "상위 3개 센터" 등)을 찾았다. v5는 동결 전이라 규칙을 고쳐 다시 쟀고 두 측정을 함께 적는다.
- 깨끗한 비교에는 v5 규칙을 보지 않은 사람이 쓴 새 평가 세트가 필요하다. 사용자 확인 뒤 `eval/golden_set_v5.json`으로 동결하고 v4·v5를 함께 잰다(T24, 미정).

### 12.5 알려진 단순화

- 낱말 규칙은 표현이 바뀌면 놓친다. 놓치면 v4와 같이 동작하고(도구 실행), 잘못 걸리면 도구로 맞힐 질문을 SQL 단계로 보낸다. SQL 단계는 지표 계산이 약하다(사례 3).
- 정렬 방향 규칙은 한 질문에 두 방향의 낱말이 있으면 손대지 않는다.
