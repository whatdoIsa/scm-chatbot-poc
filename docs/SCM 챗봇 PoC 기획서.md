# SCM 챗봇 PoC 기획서

Nov 12, 2026 · @송헌

회사 스택(Spring Boot + React + PostgreSQL)으로 SCM 자연어 질의 챗봇을 만들고, 30문항 골든셋으로 정확도를 수치로 측정해 v0에서 v2까지 개선 전후를 비교하는 PoC 기획서입니다. 마감은 11/15(일), 예산은 0원입니다.

## 1. 목표와 성공 기준

이 PoC가 증명하려는 것은 한 문장입니다. **"LLM에게 SQL 생성만 맡기고 실행·검증은 서버가 하도록 설계하면 SCM 질의 응답 정확도를 수치로 올릴 수 있고, 나는 그 과정을 측정하고 설명할 수 있다."**

### 전제 조건 (확정)

| 항목 | 내용 |
| --- | --- |
| 마감 | 11/15(일) 밤 |
| 예산 | 0원 (유료 API 사용 안 함, 무료 티어 또는 로컬 모델만 사용) |
| 가용 시간 | 오늘(목) 저녁 약 3시간 + 금·토·일 하루 4\~5시간으로 가정 |
| 최대 범위 | v2까지 (v3은 하지 않음) |

기능의 화려함은 중요하지 않습니다. 면접에서 가치가 있는 것은 (1) 회사와 같은 스택으로 만들었다는 점, (2) 정확도를 숫자로 쟀다는 점, (3) 틀린 이유를 분류해 개선했다는 점, (4) 무료 한도라는 제약 안에서 측정을 설계했다는 점입니다.

## 2. 범위와 회사 스택 매핑

회사가 쓰는 기술(Spring + React, PostgreSQL, MyBatis·JPA·프로시저)을 **용도에 맞게 써 보는 것**이 이 PoC의 두 번째 목적입니다. 그래야 "왜 섞어 쓰는가"라는 면접 질문(Q&A 파트 C)에 경험으로 답할 수 있습니다. 일정과 예산 때문에 QueryDSL은 이번 범위에서 뺍니다.

### 기술 스택

| 영역 | 선택 | 비고 |
| --- | --- | --- |
| 백엔드 | Java + Spring Boot (Gradle) | 버전은 설치된 JDK에 맞춰 최신 안정 버전 사용 |
| 프런트엔드 | React + TypeScript (Vite) | 최소 화면 한 개 (권장 항목) |
| DB | PostgreSQL (Docker Compose로 실행) | pgvector 확장은 이번에 사용하지 않음 (RAG 제외) |
| LLM 연동 | LlmClient 인터페이스 + 구현체 | 무료 외부 API 또는 로컬 모델만 사용. 선택지와 제약은 8장 |
| 테스트 | JUnit | LlmClient 가짜 구현(고정 응답)으로 파이프라인 테스트 |

### ORM·SQL 방식을 어디에 쓰는가

| 방식 | 이 PoC에서의 용도 | 회사에서 쓰는 이유와의 연결 |
| --- | --- | --- |
| JPA | 골든셋 문항, 평가 실행(eval\_run), 문항별 결과(eval\_result), 대화 로그 저장 | 단순 저장은 생산성이 높음 |
| MyBatis | 평가 결과 집계 리포트(버전별·유형별 정확도, 오답 원인별 건수), 데이터 검증 쿼리 | 집계는 SQL을 직접 제어하는 것이 유리 |
| JDBC(JdbcTemplate) | LLM이 만든 SQL을 읽기 전용 계정으로 실행 | 실행 시점에 SQL이 정해지는 동적 쿼리라 매퍼 방식과 맞지 않음. 이유를 설명할 수 있어야 함 |
| DB 함수·프로시저 | 시드 데이터 생성 (PL/pgSQL) | 대량 생성·반복 계산을 DB 안에서 |
| QueryDSL | 이번에는 쓰지 않음 | 면접에서는 "조건이 바뀌는 조회에 타입 안전성"이라는 개념으로 설명 |

### 포함하는 것

- 자연어 질문 → LLM이 SQL·되묻기·거부 중 하나를 JSON으로 선택 → SQL 검증 → 읽기 전용 실행 → 결과와 근거 반환
- 읽기 전용 DB 계정, SELECT 검증, 타임아웃 같은 최소 안전장치
- 골든셋 기반 자동 평가와 v0 → v1(→ v2) 버전별 비교
- (권장) 최소 React 화면에서 결과 표와 근거 SQL·기준일 표시

### 제외하는 것 (일부러 뺌)

- 조회 도구 호출(MyBatis 고정 쿼리), 숫자 후검증, 라우터 분리 (v3 범위)
- RAG(pgvector), 테넌트 격리(RLS), QueryDSL
- 결과를 LLM이 문장으로 풀어 쓰는 단계. 결과는 표로 보여주고, 정확도는 SQL 실행 결과로 평가합니다 (무료 한도 절약, 8장 참고)
- 로그인·회원가입, 결제, 관리자 화면
- 실제 수요예측 모델 학습. 예측값은 **가짜 예측 테이블**로 두고 정확도(WMAPE) 계산에만 사용
- Rust, 운영 배포, 성능 최적화, 대규모 데이터

**범위 원칙**: 일정이 밀리면 React 화면 → v2 → 골든셋 문항 수(30 → 20) 순서로 줄입니다. 데이터, 챗봇 API, 골든셋과 평가 실행기, v0 → v1 비교는 끝까지 남깁니다.

## 3. 아키텍처와 요청 흐름

LLM은 SQL(또는 되묻기·거부)만 만들고, 실행과 검증은 서버가 맡습니다. 그림의 강조 박스(SQL 검증)가 v2에서 정확도와 안전을 함께 올리는 지점입니다.

&#91;embedded content: 챗봇 요청 흐름 · LLM 호출 1회, 처리 경로 3개 (SQL·되묻기·거부)\]

### 요청 흐름

1. React 화면이 질문을 Spring Boot API로 보냅니다.
2. API가 프롬프트를 조립합니다: 기준일, 지표 사전(v1), 질문과 관련된 테이블 스키마만(v2).
3. LLM을 1회 호출해 JSON으로 SQL, 되묻기, 거부 중 하나를 받습니다.
4. 되묻기·거부는 DB를 거치지 않고 바로 응답합니다.
5. SQL이면 검증(SELECT 한 문장, 허용 테이블, LIMIT)을 통과해야 읽기 전용 계정으로 실행합니다. 실행 오류가 나면 오류 메시지를 붙여 1회 재시도합니다(v2).
6. 결과 표와 근거 SQL·기준일을 응답하고, 질문·SQL·결과·소요 시간을 JPA로 저장합니다. 평가 실행기는 이 흐름을 화면 없이 그대로 호출합니다.

### 구현 포인트

- v0, v1, v2는 같은 코드에서 프롬프트 조립과 검증 단계의 **켜고 끄기**만 달라지도록 만들면, 버전별 실험이 설정 변경만으로 끝납니다.
- Text-to-SQL이 쓰는 DB 연결은 읽기 전용 계정으로 분리하고, 로그·평가 저장용 연결과 섞지 않습니다.
- LLM 호출부(`LlmClient`)는 인터페이스 뒤에 두어 모델 교체와 테스트용 가짜 구현이 쉽게 합니다. 개발·디버깅은 가짜 구현으로 하고, 무료 한도는 공식 평가 실행에만 씁니다.
- 결과를 LLM이 문장으로 풀어 쓰는 단계는 넣지 않습니다. 호출 수와 토큰을 절반으로 줄이고, 평가를 SQL 실행 결과 기준으로 단순하게 하기 위함입니다.

## 4. 데이터 설계

가짜 데이터는 **고정 시드로 생성해 항상 같은 값이 나오게** 합니다. 그래야 골든셋의 정답이 흔들리지 않습니다. 규모는 50개 SKU × 5개 거점 × 최근 90일로, 전체 약 4.9만 행입니다.

### 테이블 (6개, 컬럼명은 영어 snake\_case)

| 테이블 | 의미 | 주요 컬럼 | 행 수(약) |
| --- | --- | --- | --- |
| product | 품목 | sku(PK), name, category, unit\_cost, abc\_class | 50 |
| location | 거점(물류센터·매장) | location\_id(PK), name, region | 5 |
| sales\_daily | 일별 판매 실적 | sale\_date, sku, location\_id, qty | 22,500 |
| inventory\_daily | 일별 재고 스냅샷 | snap\_date, sku, location\_id, on\_hand, in\_transit | 22,500 |
| forecast\_weekly | 주별 예측(가짜 예측값) | week\_start, sku, location\_id, forecast\_qty | 3,250 (13주) |
| supply\_policy | 공급 정책 | sku, location\_id, lead\_time\_days, safety\_stock, reorder\_point | 250 |

컬럼 이름은 영어로 두고, 한국어 질문과의 대응(예: "재고" → on\_hand, "거점" → location)은 5장의 지표 사전에서 관리합니다. 이렇게 해야 LLM이 이름을 추측하지 않습니다.

### 데이터에 일부러 넣을 패턴

질문에 의미 있는 답이 나오도록, 생성 스크립트에서 다음을 의도적으로 심습니다.

- 요일 효과와 완만한 추세 (판매량이 평평하지 않게)
- 프로모션성 급증 구간이 있는 SKU 몇 개
- 재고가 0이 되는(결품) 구간이 있는 SKU-거점 몇 개
- 예측이 크게 빗나간 SKU 몇 개 (WMAPE 순위 질문용)
- 안전재고에 못 미치는 SKU-거점 몇 개

### 생성 방식

- PostgreSQL의 generate\_series와 고정 시드(setseed) 기반 SQL 또는 PL/pgSQL 함수로 생성 (회사의 "프로시저 방식" 경험 포인트)
- 한 번에 재생성할 수 있는 스크립트(`db/seed.sql`)로 관리
- **기준일(as\_of\_date)을 설정값으로 고정**: 데이터의 마지막 날을 "오늘"로 간주합니다. "지난달", "최근 7일" 같은 상대 표현이 항상 같은 기간으로 해석되게 하기 위함이며, 프롬프트에도 기준일을 주입합니다.

### 지표 정의 (PoC 기준, 5장 지표 사전과 동일)

| 지표 | 정의 |
| --- | --- |
| 일평균 판매량 (최근 N일) | 최근 N일 qty 합계 ÷ N |
| 재고보유일수 | 기준일 on\_hand ÷ 최근 28일 일평균 판매량 |
| 결품률 | 기간 내 on\_hand = 0인 (SKU, 거점, 일) 수 ÷ 전체 (SKU, 거점, 일) 수 |
| 안전재고 미달 | 기준일 on\_hand < safety\_stock |
| 재주문 필요 | 기준일 on\_hand + in\_transit ≤ reorder\_point |
| 예측 정확도 | 1 − WMAPE (주 단위) |

```latex
\text{재고보유일수} = \frac{\text{기준일 현재고}}{\text{최근 28일 일평균 판매량}}
```

```latex
\text{WMAPE} = \frac{\sum |\text{실적} - \text{예측}|}{\sum \text{실적}}
```

지표 정의(예: 28일 기준)는 PoC가 임의로 정한 것입니다. 실제 회사마다 정의가 다르다는 점이 곧 "지표 사전이 필요한 이유"이므로, 면접에서 그대로 활용하세요.

## 5. 챗봇 설계

핵심 원칙은 **숫자는 DB 조회 결과에서만 나오고, LLM은 질문 해석과 SQL 작성만 맡는다**입니다. 이번 범위에서는 질문 한 개당 LLM 호출을 1회로 두어 무료 한도를 아낍니다.

### LLM 출력 형식

LLM은 아래 JSON 하나만 반환합니다. 형식을 지키지 못하면 오답으로 처리하고, 그 비율도 지표로 기록합니다.

| action | 의미 | 서버가 하는 일 |
| --- | --- | --- |
| sql | 데이터를 조회하는 SQL을 작성 | 검증을 통과하면 읽기 전용 계정으로 실행 |
| clarify | 질문이 모호해 되물어야 함 | message(되묻는 문장)를 그대로 응답 |
| refuse | 쓰기 요청, 범위 밖 요청, 데이터가 없는 기간 | message(거부 사유)를 그대로 응답 |

### 질문 유형과 기대 동작

| 유형 | 예시 질문 | 기대 action |
| --- | --- | --- |
| 단순 조회 | "SKU-007의 현재 재고는?" | sql |
| 기간 집계 | "지난주 서울센터 총 판매량은?" | sql (기준일 기준 기간 해석) |
| 지표 계산 | "재고보유일수가 가장 짧은 품목 5개는?" | sql (4장 지표 정의를 따름) |
| 비교·순위 | "예측 정확도가 가장 낮은 SKU는?" | sql |
| 모호한 질문 | "재고 어때?" | clarify (품목·거점·기간 확인) |
| 거부·안전 | "재고를 0으로 수정해줘", "3월 판매량은?" (데이터에 없는 기간) | refuse |

### 버전별 구성

| 버전 | 프롬프트에 넣는 것 | 서버가 하는 일 |
| --- | --- | --- |
| v0 기준선 | 전체 테이블 스키마(DDL) + 질문 + 출력 형식 | 읽기 전용 계정으로 실행, 타임아웃만 적용 |
| v1 | v0 + 기준일, 지표 사전, 날짜 해석 규칙, few-shot 예시 | v0과 동일 |
| v2 | v1에서 스키마를 질문과 관련된 테이블로 축소 | SELECT 검증(단일 문장, 허용 테이블, LIMIT 자동 부여), 실행 오류 시 오류 메시지를 붙여 1회 재시도 |

두 가지 규칙을 지킵니다.

- **few-shot 예시는 골든셋 30문항과 겹치지 않게** 따로 만듭니다 (5개 내외). 겹치면 정답을 알려 주고 시험을 보는 셈이라 점수가 부풀려집니다.
- v2의 스키마 축소는 LLM이 아니라 **키워드 규칙**(예: "판매" → sales\_daily, product)으로 선택합니다. 호출 수를 늘리지 않기 위해서입니다.

### 지표 사전 (Semantic Layer)

한국어 표현과 DB 컬럼·지표 정의를 한 파일(`metrics.yml`)로 관리하고, v1부터 프롬프트에 넣습니다. v2에서는 질문과 관련된 항목만 골라 넣습니다.

| 사용자 표현 | 매핑 |
| --- | --- |
| 재고, 현재고 | inventory\_daily.on\_hand (기준일) |
| 거점, 센터, 창고 | location |
| 판매량, 출고량 | sales\_daily.qty |
| 재고보유일수 | 4장 정의 (28일 기준) |
| 결품률 | 4장 정의 |
| 지난주, 지난달, 최근 7일 | 기준일 기준의 날짜 범위 규칙 |

### 안전장치

- **항상 적용 (v0부터)**: 읽기 전용 DB 계정(SELECT만 허용)으로 별도 연결, 쿼리 타임아웃(statement\_timeout)
- **v2에서 추가**: 단일 SELECT 문만 통과, 허용된 테이블 외 접근 차단, LIMIT 자동 부여, 실행 오류 시 1회 재시도
- 실행한 SQL과 결과 건수를 로그와 화면의 근거 영역에 남김

### 응답 규칙과 재현성

- 근거(조회 결과)가 없으면 "데이터에서 확인되지 않습니다"라고 답합니다. 추측하지 않습니다.
- 응답에는 기준일, 기간, 사용한 지표 정의를 함께 표시합니다.
- 같은 모델, temperature는 낮게 고정하고, 프롬프트는 버전 파일(`prompts/v0.txt` \~ `v2.txt`)로 관리합니다. 평가 결과에는 사용한 모델 이름과 설정을 함께 저장해 실험을 재현할 수 있게 합니다.

## 6. 골든셋과 평가·개선 실험

이 장이 PoC의 핵심입니다. 같은 30문항, 같은 모델, 같은 설정으로 버전별 점수를 비교하고, 틀린 이유를 분류해 개선합니다.

### 골든셋 30문항 구성

| 유형 | 문항 수 | 채점 방식 |
| --- | --- | --- |
| 단순 조회 | 6 | 생성 SQL 실행 결과가 정답 SQL 결과와 일치 |
| 기간 집계 | 8 | 동일 (기간 해석 포함) |
| 지표 계산 | 6 | 동일 (숫자는 허용 오차 0.1% 이내) |
| 비교·순위 | 4 | 상위 N개 목록과 순서까지 일치 |
| 모호한 질문 | 2 | action이 clarify |
| 거부·안전 | 4 | action이 refuse (쓰기 요청, 범위 밖 요청, 데이터 없는 기간) |

### 문항 예시 (이 형식으로 30개를 채웁니다)

| 질문 | 유형 | 정답 기준 |
| --- | --- | --- |
| SKU-007의 현재 재고는? | 단순 조회 | 정답 SQL 실행 결과 |
| 지난주 서울센터 총 판매량은? | 기간 집계 | 정답 SQL (기준일 기준 지난주) |
| 최근 7일 일평균 판매량이 가장 높은 품목 3개는? | 비교·순위 | 상위 3개 순서 |
| 재고보유일수가 7일 미만인 SKU-거점 수는? | 지표 계산 | 정답 SQL 실행 결과 |
| 최근 13주 예측 정확도가 가장 낮은 SKU 5개는? | 비교·순위 | WMAPE 기준 하위 5개 |
| 재고 어때? | 모호 | action = clarify |
| SKU-007 재고를 0으로 바꿔줘 | 거부·안전 | action = refuse |
| 3월 판매량은? (데이터에 없는 기간) | 거부·안전 | action = refuse |

### 정답 만드는 방법

- 문항마다 **사람이 직접 정답 SQL을 작성**하고(`eval/golden_set.json`), 평가 때 그 SQL을 실행해 기대값을 얻습니다. 값을 손으로 적지 않으므로 데이터가 재생성돼도 정답이 따라옵니다.
- 정답 SQL 자체가 틀릴 수 있으므로, 5문항 정도는 손계산이나 스프레드시트로 교차 확인합니다.
- 골든셋은 **v0을 돌리기 전에 30개를 확정**합니다. 개발 중에 프롬프트를 보며 문항을 만들면 "시험 문제를 보고 답을 맞춘" 결과가 됩니다. 이후 새로 발견한 오답 유형은 별도 문항으로 추가하되, 점수 비교는 처음 30문항으로 유지합니다.

### 평가 지표

- 전체 정확도, 유형별 정확도
- SQL 실행 성공률 (오류 없이 실행된 비율), JSON 형식 준수율
- 평균 응답 시간, 호출 수와 토큰 사용량 (실제 측정값)
- **오답 원인 분류**: 스키마 오해, 지표 정의 오류, 기간 해석 오류, 조인·집계 오류, action 선택 오류(되묻기·거부 실패), 형식 오류

이번 범위에서는 LLM이 결과를 문장으로 풀어 쓰는 단계를 넣지 않았으므로, 평가는 **SQL 실행 결과 일치와 action 선택**만 봅니다.

### 개선 실험 계획 (버전별)

| 버전 | 변경 내용 | 확인하려는 가설 |
| --- | --- | --- |
| v0 기준선 | 전체 스키마만 주고 LLM이 바로 SQL 생성 | 아무 장치 없이는 어디서 틀리는가 |
| v1 지표 사전 | v0 + 기준일, 지표 사전(metrics.yml), 날짜 규칙, few-shot 예시 | 지표·기간 오류가 줄어드는가 |
| v2 스키마 축소 + 검증 | v1 + 관련 테이블만 제공, SELECT 검증, 오류 시 1회 재시도 | 조인·집계 오류와 실행 실패가 줄어드는가 |

### 호출·토큰 예산 (무료 한도 안에서 실행하기)

예산이 0원이므로 무료 한도 안에서 호출량을 먼저 계산합니다. 아래 수치는 프롬프트를 만들기 전의 \*\*어림값(추정)\*\*이며, 금요일에 실제 프롬프트 길이를 재서 고칩니다.

| 버전 | 호출당 토큰(추정) | 30문항 1회 토큰(추정) |
| --- | --- | --- |
| v0 | 약 1,500 | 약 45,000 |
| v1 | 약 3,000 | 약 90,000 |
| v2 | 약 2,500 | 약 75,000 (재시도가 생기면 증가) |
| 합계 |  | 약 21만 토큰, 호출 약 90회 + 재시도 |

- 8장에서 확인한 Groq 무료 샘플 한도(2026-09 기준 자료)는 분당 약 8천 토큰, 하루 약 20만 토큰입니다. 이 기준이면 **하루에 전체 실행을 한 번 하기도 빠듯하므로**, 토요일에 v0·v1, 일요일에 v2처럼 하루 한도에 맞춰 나눠 실행합니다. Gemini 등 다른 선택지는 본인 계정의 콘솔에서 한도를 확인해야 합니다.
- 호출당 약 3천 토큰이면 분당 2\~3회만 가능하므로 30문항 실행에 10\~15분이 걸립니다. 실행기에 호출 간격과 429(한도 초과) 응답 시 대기 후 재시도를 넣고, **이 대기 시간에 React 화면을 만듭니다.**

- 작업 전에 `AGENTS.md`에 적을 것: 빌드·테스트 명령, 계층 규칙(Controller → Service → Mapper), 트랜잭션 규칙, 필드 주입 금지, 엔티티를 API 응답으로 반환 금지, 비밀 값(API 키)을 코드나 저장소에 넣지 않기
- AI가 만든 코드는 **컴파일·테스트·직접 읽기**로 검증하고, 특히 트랜잭션 경계, 쿼리, 안전장치(읽기 전용 계정, SELECT 검증) 부분은 반드시 직접 확인
- AI가 낸 실수를 발견하면 `docs/ai-mistakes.md`에 한 줄 기록하고, 반복될 것 같으면 `AGENTS.md` 규칙이나 테스트로 승격
- 골든셋 평가 자체가 "챗봇용 테스트 하네스"이므로, 프롬프트나 모델을 바꿀 때마다 같은 골든셋으로 다시 실행
- 이 기록이 면접의 "AI가 만든 코드를 어떻게 믿는가" 질문에 쓸 실제 사례가 됩니다.

## 8. 위험과 결정 필요 사항

### 무료 LLM 선택지 (예산 0원)

아래는 2026년 9\~10월 시점의 외부 자료 기준이며, 무료 한도는 자주 바뀝니다. **오늘 저녁에 본인 계정의 콘솔에서 실제 한도를 확인**하고 6장의 예산 표를 고치세요.

| 선택지 | 확인된 내용 | 이 PoC에서의 약점 |
| --- | --- | --- |
| A. Groq 무료 티어 | 카드 없이 키 발급이 가능하다는 자료가 있음(가입 때 직접 확인). 모델별 샘플 한도로 gpt-oss-120b 등이 분당 30회, 일 1,000회, 분당 8천 토큰, 일 20만 토큰으로 안내됨 | 일 토큰 한도가 병목. 전체 평가를 하루 한 번 하기도 빠듯함 |
| B. Gemini API 무료 티어 (Google AI Studio) | 무료 티어가 있고, 한도는 모델마다 다르며 공식 문서는 AI Studio 콘솔에서 확인하라고 안내함. 일일 한도는 태평양 시간 자정에 초기화됨 | 자료마다 수치가 달라 이 문서에서는 확정하지 않음. 본인 계정에서 확인 필요 |
| C. 로컬 Ollama | 비용 0원, 호출 제한 없음, 3회 반복 측정 가능. RAM 8GB는 작은 모델, 16GB 이상이면 쾌적하고 GPU 없이도 CPU로 실행 가능하다는 가이드가 많음. SQL에는 qwen2.5-coder 7B 같은 코드 모델이 권장됨 | PC 사양에 따라 느릴 수 있고, 작은 모델은 정확도가 낮거나 한국어 질문에서 편차가 큼 |

**제안**: 오늘 저녁 (1) PC의 RAM과 GPU 확인 → (2) A 또는 B의 키 발급 시도(약 10분) → (3) 공식 측정은 **한 모델로 고정**합니다. v0\~v2를 서로 다른 모델로 돌리면 개선 효과인지 모델 차이인지 알 수 없어서 비교가 깨집니다. A·B가 막히면 C로 진행합니다. 실제 회사나 개인 데이터는 넣지 않고 가짜 데이터만 외부 API에 보냅니다.

## 9. 요구사항 정의 (PRD)

이 장부터 12장까지는 구현 담당(Claude Code)이 그대로 읽고 작업할 수 있게 쓴 명세입니다. 앞 장(1\~8장)과 충돌하면 **이 장 이후가 우선**합니다.

### 9.1 목적과 사용자

- **목적**: SCM 계획 담당자가 한국어로 재고·판매·예측 질문을 하면, LLM이 SQL을 만들고 서버가 검증·실행해 정확한 결과를 돌려주는 챗봇의 PoC. 핵심 산출물은 챗봇 자체가 아니라 **골든셋 기반 정확도 측정과 v0 → v2 개선 비교**입니다.
- **사용자(가정)**: 수요·재고 계획 담당자. 질문은 한국어 자연어이고, 기준일은 데이터의 마지막 날(2026-11-08)입니다.
- **환경**: MacBook Air M2 24GB 한 대에서 전부 실행합니다. 유료 서비스는 사용하지 않습니다 (예산 0원).

### 9.2 핵심 시나리오

| 시나리오 | 사용자 입력 | 기대 결과 |
| --- | --- | --- |
| 조회 | "SKU-007의 현재 재고는?" | action = sql, 결과 표 1행, 근거 SQL과 기준일 표시 |
| 모호한 질문 | "재고 어때?" | action = clarify, 품목·거점·기간을 되묻는 문장 |
| 위험한 요청 | "SKU-007 재고를 0으로 바꿔줘" | action = refuse, 쓰기 불가 사유 |
| 평가 | 터미널에서 평가 실행 | 30문항 채점 후 전체·유형별 정확도와 오답 원인 출력, DB에 저장 |

### 9.3 기능 요구사항

| ID | 요구사항 | 우선순위 | 수용 기준 |
| --- | --- | --- | --- |
| FR-01 | 시드 데이터 생성: `db/seed.sql` 하나로 6개 SCM 테이블을 결정적으로 생성 | 필수 | 11장의 행 수 검증 쿼리가 모두 일치하고, 재실행해도 체크섬 쿼리 결과가 동일 |
| FR-02 | 챗봇 API: `POST /api/chat` (10장) | 필수 | 3가지 action 응답이 10장 형식을 지킴 |
| FR-03 | LLM 호출 추상화: `LlmClient` 인터페이스, `OllamaLlmClient`, `FakeLlmClient` | 필수 | 설정만 바꿔 구현체 전환, Fake로 전체 테스트 통과 |
| FR-04 | 프롬프트 버전 v0/v1/v2를 설정값(`chat.prompt-version`)으로 전환 | 필수 | 버전별로 `prompts/` 파일이 달라지고 응답에 사용 버전이 기록됨 |
| FR-05 | 읽기 전용 실행: 별도 DataSource(읽기 전용 계정)로만 LLM 생성 SQL 실행, 타임아웃 적용 | 필수 | INSERT/UPDATE/DELETE 시도가 DB 권한으로 거부되는 통합 테스트 |
| FR-06 | SQL 검증(v2에서 활성): 단일 SELECT, 허용 테이블 6개, LIMIT 자동 부여 | 필수 | 통과 5개·거부 10개 이상의 단위 테스트 |
| FR-07 | 실행 오류 시 오류 메시지를 붙여 1회 재시도 (v2에서 활성) | 권장 | Fake 클라이언트로 재시도 1회 후 성공·실패 케이스 테스트 |
| FR-08 | 골든셋 30문항(`eval/golden_set.json`) 로더와 형식 검증 | 필수 | 유형별 문항 수(6/8/6/4/2/4) 검증 테스트, 정답 SQL이 모두 실행 가능 |
| FR-09 | 평가 실행기(`eval` 프로파일): 문항별 채점, 결과를 `eval_run`·`eval_result`에 저장, 콘솔 리포트 | 필수 | 실행 후 전체·유형별 정확도, SQL 실행 성공률, JSON 형식 준수율, 평균 시간 출력 |
| FR-10 | 평가 요약 조회: `GET /api/eval/summary` (MyBatis 집계) | 권장 | 버전별·유형별 정확도와 오답 원인별 건수 반환 |
| FR-11 | 대화 로그 저장(JPA): `chat_log` | 필수 | 질문 1건당 1행 저장 |
| FR-12 | React 최소 화면: 질문 입력, action별 표시, 결과 표, 근거 SQL·기준일 | 권장 | 3가지 시나리오를 화면에서 수동 확인 |

**채점 규칙 (FR-09 상세)**

- sql 유형 문항: 생성 SQL의 실행 결과가 정답 SQL의 실행 결과와 같으면 정답. 컬럼 이름은 무시하고 값만 비교합니다. 숫자는 상대 오차 0.1% 이내, 순위 문항은 행 순서까지 일치해야 합니다.
- clarify 문항: action = clarify면 정답. refuse 문항: action = refuse면 정답.
- 오답이면 `error_type`을 기록합니다: SCHEMA\_MISUNDERSTANDING, METRIC\_DEFINITION, DATE\_RANGE, JOIN\_AGGREGATION, ACTION\_MISMATCH, FORMAT\_ERROR, SQL\_EXECUTION\_ERROR. 자동으로 가릴 수 있는 것(실행 오류, action 불일치, 형식 오류)만 자동 기록하고, 나머지는 사람이 평가 후 수정합니다.
